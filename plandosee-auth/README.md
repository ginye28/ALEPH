## 로그인 뒤에야 보입니다

가입·로그인·로그아웃은 **Supabase Auth**(이메일+비밀번호)가 처리합니다. 로그인 전에는
로그인 화면만 보이고, 로그인 뒤에는 **내 계정으로 만든 계획·할일·실행기록만** 보입니다 —
접근 통제는 화면 조건문이 아니라 **DB의 RLS(Row Level Security) 정책**이 겁니다. 남의
계획 id를 직접 주소에 넣어 열어 봐도 서버가 거절합니다(검사 26~29).

비밀번호는 이 앱이 직접 저장하지 않습니다. Supabase Auth가 bcrypt로 해시해 관리합니다.

## 실행

```bash
npm install
```

```bash
npm run dev
```

개발 서버는 <http://localhost:5178> 에 열립니다. 빌드는 `npm run build`.

Supabase 프로젝트의 URL·publishable key를 `.env.local`에 넣어야 실제 저장소로 동작합니다
(과제 6의 `plandosee` 프로젝트와는 **다른** 새 Supabase 프로젝트입니다):

```
VITE_SUPABASE_URL=...
VITE_SUPABASE_ANON_KEY=...
```

없으면 화면에 경고가 뜨고 임시 메모리 저장소로 동작합니다(새로고침하면 사라짐).

## 검증 안내서

**어디로 가나요** — 공개 주소 (로그인 화면부터 시작)

**무엇을 하나요** (3단계)

1. 새 계정으로 **가입**한다.
2. **로그인**해 계획 하나를 만든다.
3. **로그아웃**한 뒤 같은 자료 화면 주소를 다시 연다.

**무엇이 보이면 통과인가요**

- 1단계 — 가입 직후 자동으로 로그인되거나 로그인 화면으로 이동한다.
- 2단계 — 만든 계획이 **내 화면에만** 보인다.
- 3단계 — 로그아웃 뒤에는 로그인 화면만 보이고 자료는 보이지 않는다.

**안 될 때**

- 가입이 안 되면 이미 있는 이메일인지 오류 문구를 읽는다.
- 로그인 후에도 로그인 화면이면 새로고침 한 번 해 본다(세션 반영 지연).
- 자료가 안 보이면 계정을 잘못 골랐는지(다른 계정으로 가입했는지) 확인한다.

## 알아둘 설계 결정

과제 6에서 검증된 원칙(행은 `id`로 가리킴, 날짜는 문자열 비교, 가져오기는 읽기→검사→쓰기,
잘못된 값은 보류로 남김, 이력 테이블은 append-only)은 그대로 가져옵니다. 자세한 내용은
[플랜두씨-다이어리-설계도.md](../플랜두씨-다이어리-설계도.md)를 참고하세요.

이번 과제에서 새로 추가한 원칙:

**소유자는 클라이언트가 아니라 서버가 정합니다.** `user_id`는 요청 본문의 값을 무시하고
`stamp_owner()` 트리거가 항상 `auth.uid()`로 덮어씁니다. 클라이언트가 남의 계정 id를
적어 보내도 소용없습니다(검사 29).

**화면에서 숨기는 것과 서버가 거절하는 것은 다릅니다.** 모든 접근 통제는 RLS 정책으로
겁니다. 목록에서만 안 보이게 하는 것으로는 부족합니다 — URL을 직접 쳐도 열리면 안 됩니다.

**비밀번호는 손으로 다루지 않습니다.** 저장·비교·재설정 전부 Supabase Auth(GoTrue)에
맡깁니다. 캡처에 남는 비밀번호·토큰 문자열은 항상 가림 처리합니다.

**로그아웃은 액세스 토큰까지 즉시 죽입니다.** JWT는 stateless라 `auth.uid()`만 보면
로그아웃해도 서명은 만료 전까지 유효합니다. 그래서 모든 RLS 정책이 `session_is_active()`로
토큰의 `session_id`가 `auth.sessions`에 지금도 있는지 함께 검사합니다 — 로그아웃하면 그 행이
지워지므로 상태 코드는 그대로 200이어도 자료는 0건입니다(검사 23).
