# AI가 바뀌어도 작업 이어가기 — 설계도

한 AI가 중단되거나 다른 AI로 바뀌어도 **저장소와 인계 문서만으로** 같은 작업을 이어가는 실험. 정해진 예산 안에서 모델을 바꿔 쓰고, 두 AI의 작업을 같은 단위로 비교해 앞으로의 선택 기준을 만든다.

개선 대상은 **과제 4 `today-dashboard`**(<https://aleph-dash.vercel.app>)다. 이미 배포·촬영 도구(`tools/capture.mjs`, CDP 직접 제어)가 있어 **검사를 명령으로 판정하는 비용이 거의 0**이기 때문이다. 이 과제의 점수는 기능이 아니라 인계에서 나오므로, 측정 도구를 새로 배우는 데 예산을 쓰지 않는다.

---

## 0. 이 설계도의 기준

과제 카드 5개는 아래 **네 가지 설계 원칙**에서 따라 나온다. 구현 중 판단이 갈리면 이 네 줄로 되돌아온다.

| # | 원칙 | 이 원칙이 막아주는 실패 |
|---|------|------------------------|
| 1 | **검사 10개의 통과·실패는 사람 눈이 아니라 `node tools/check.mjs` 한 줄이 판정한다.** 번호 1~10이 그대로 출력된다. | AI가 "다 됐습니다"라고 말한 것이 기준이 되어, 두 AI 비교가 측정이 아니라 인상평으로 끝나는 문제 (카드 1·5의 핵심) |
| 2 | **화면에 보이는 인계 문서와 비교 표는 저장소 파일 하나에서만 나온다.** `HANDOFF.md`와 `worklog.json`을 화면이 직접 읽는다. | 문서용 사본과 화면용 사본이 따로 관리돼 "문서에는 통과, 화면에는 실패"로 어긋나는 문제 (카드 3의 핵심) |
| 3 | **AI B에게 주는 입력은 저장소 + `HANDOFF.md` 뿐이다.** 첫 대화 전문은 어떤 경로로도 넘기지 않는다. | 인계 문서가 실제로 쓸 만한지 검증되지 않고, 사람의 기억이 문서를 대신 메워버리는 문제 (카드 4의 핵심) |
| 4 | **기존 계산 함수는 건드리지 않는다. 선택 단계를 앞에 붙인다.** `computeDiff()`는 그대로 두고 `selectPair()`를 새로 만든다. | 개선 하나 때문에 과제 4의 통과 기준이 깨져, AI B가 남은 작업 대신 회귀 수정에 예산을 다 쓰는 문제 (회귀 검사 3개의 근거) |

> **구현 기록 (2026-08-24)** — 카드 1~3까지 구현했다. 설계와 달라진 곳은 세 군데다.
> ① `check.mjs`가 구역을 **본문 글자가 아니라 제목(h2)으로** 찾는다 — 비교 영역이 "아래 날짜별
> 기록에서…"라고 안내 문구에 쓰는 순간 본문 검색이 엉뚱한 구역을 잡았다.
> ② 시작 상태 측정 결과 **검사 1은 손대기 전부터 통과**였다(과제 4의 기존 동작). 그래서 선택 기능이
> 들어가자마자 통과가 3→8로 뛰며 "검사 6개 통과" 중단 조건이 바로 걸렸다. 남은 것은 **6·7 두 개**로,
> §7의 예시(6·7·8·10)보다 적다. ③ `vite.config.js`의 기본 포트를 5175로 맞췄다 — 인계 문서의
> `npm run dev`가 포트 플래그 없이 그대로 작동해야 하기 때문이다.

> **예산 원칙** — 무료 한도를 일부러 소진하지 않는다. 상한은 이미 이용 가능한 무료 범위의 **절반 이하**로 잡고, 도달하면 그 자리에서 멈춘다. 개인 결제를 새로 하지 않는다.

## 1. 무엇을 개선하는가 (카드 1)

**기능 문장** — 카드 1이 요구하는 `사용자가 ______하면 ______가 된다` 한 문장:

> **사용자가 날짜별 기록에서 한 건을 누르면, 그 날짜가 비교 기준이 되고 차이·방향·단위가 즉시 다시 계산된다.**

**화면에 보일 이름과 사용 방법** (완료 기준 1) — 비교 영역 제목 옆에 한 줄로 고정한다.

```
비교 기준 고르기 — 아래 기록을 누르면 그 날짜와 비교합니다
```

### 후보 비교

| 후보 | 한 번 조작으로 화면이 바뀌는가 | 회귀 위험 | 4~5시간 안에 끝나는가 | 판정 |
|------|------------------------------|-----------|----------------------|------|
| **비교 기준 날짜 고르기** | 기록을 누르면 차이 숫자가 즉시 바뀜 | 낮음 — 읽기 쪽만 바뀜, 저장 형식 그대로 | 예 | **★★★ 선택** |
| 기준 시각 09시 → 임의 시각 선택 | 바뀜 | 높음 — 저장 형식과 중복 방지 규칙을 함께 고쳐야 함 | 아니오 | ★☆☆ |
| °C ↔ °F 단위 전환 | 바뀜 | 낮음 | 예 | ★★☆ — 오류 검사 3개를 억지로 만들어야 함 |

기준 시각 선택기는 기능으로는 더 그럴듯하지만 **저장 형식 변경**을 부른다. 저장 형식이 바뀌면 과제 4의 원칙 3(날짜 키 중복 방지)을 다시 검증해야 하고, 그 비용이 이 과제의 상한을 넘긴다. **인계를 연습하는 과제에서 기능이 예산을 다 먹으면 과제 자체가 실패한다** — 그래서 읽기 쪽만 바뀌는 후보를 고른다.

### 설계 (원칙 4)

`computeDiff()`는 이미 "배열의 앞 2건을 비교"하는 함수다. 이 함수를 고치지 않고, **앞에 선택 단계를 하나 끼운다.**

```js
// core/selectPair.js  ← 이번 과제에서 새로 만드는 유일한 계산 파일
export const selectPair = (records, baseKey) => {
    if (!Array.isArray(records) || records.length < 2) {
        return { pair: records ?? [], selected: null };
    }
    const [latest] = records;
    if (!baseKey) {
        return { pair: [latest, records[1]], selected: null };   // 기존 동작 그대로
    }
    if (baseKey === latest.dateKey) {
        return { pair: [], selected: baseKey, reason: "sameDate" };
    }
    const base = records.find((r) => r.dateKey === baseKey);
    if (!base) {
        return { pair: [latest, records[1]], selected: null, reason: "vanished" };
    }
    return { pair: [latest, base], selected: baseKey };
};
```

`Dashboard`는 `selectPair()`의 `pair`를 `computeDiff()`에 그대로 넘긴다. `computeDiff()`의 코드는 한 줄도 바뀌지 않는다 — 회귀 검사 3개가 통과할 근거가 여기서 나온다.

**선택 상태는 메모리에만 둔다.** `localStorage`에 저장하지 않는다. 채점자가 주소를 새로 열면 항상 기본(최신 2건) 비교부터 보여야 하고, 저장 형식을 건드리지 않아야 원칙 4가 유지된다.

| 상황 | `selectPair` 결과 | 화면 |
|------|------------------|------|
| 아무것도 안 누름 | 최신 2건 | 기존과 동일. 선택 표시 없음 |
| 지난 날짜 누름 | 최신 + 그 날짜 | 그 행에 선택 표시, 차이 다시 계산, `선택 해제` 버튼 등장 |
| 최신 기록 자신을 누름 | `pair` 비움 + `sameDate` | "같은 날짜끼리는 비교하지 않습니다" — **차이 숫자를 0으로 꾸미지 않는다** |
| 선택한 날짜가 사라짐(기록 지움) | 최신 2건 + `vanished` | 선택 자동 해제, 기본 비교로 복구. 빈 값·`NaN` 금지 |
| 기록 1건 이하 | 그대로 | 기존 부족 문구. 기록 행은 누를 수 없음 |

## 2. 검사 10개 (카드 1)

작업 **시작 전에** 확정하고 커밋한다. 정상 4 · 오류 3 · 기존 기능 3.

| # | 구분 | 검사 | 판정 |
|---|------|------|------|
| 1 | 정상 | 선택 없이 열면 최신 2건이 비교되고 계산식이 화면에 보인다 | 기본 비교의 두 날짜 = 기록 목록 위 2건 |
| 2 | 정상 | 지난 날짜 기록을 누르면 비교 기준이 그 날짜로 바뀐다 | 차이 숫자가 손계산 `최신값 − 선택값`과 일치 |
| 3 | 정상 | 다른 기록을 누르면 선택 표시가 옮겨간다 | 선택 표시 1개만 존재 |
| 4 | 정상 | `선택 해제`를 누르면 기본 비교로 돌아온다 | 화면이 검사 1과 같아짐 |
| 5 | 오류 | 최신 기록 자신을 누르면 사유 문구가 보이고 차이 숫자가 없다 | `같은 날짜` 문구 있음 + 숫자 없음 |
| 6 | 오류 | 기록이 1건이면 기록 행을 누를 수 없고 부족 문구가 보인다 | 클릭해도 화면 변화 0 |
| 7 | 오류 | 선택한 날짜를 점검 도구로 지우면 선택이 자동 해제된다 | `NaN`·빈 값 0건, 기본 비교 복구 |
| 8 | 회귀 | 장애 5종을 재현해도 선택 상태·기록 목록이 유지된다 | 마지막 정상값과 `오래된 데이터` 표시 그대로 |
| 9 | 회귀 | `다시 확인`을 두 번 눌러도 날짜별 기록에 중복이 없다 | 날짜 키 중복 0건 |
| 10 | 회귀 | 09시 기준·`origin` 배지·출처 링크가 그대로 보인다 | 출처 `href` = 실제 호출 주소 |

### 실행기 (원칙 1)

```
today-dashboard/tools/check.mjs      # capture.mjs의 CDP 연결부를 그대로 재사용
```

```bash
node today-dashboard/tools/check.mjs
```

출력 형식을 고정한다. 이 출력이 작업 기록·인계 문서·비교 표의 **유일한 근거**다.

```
1  PASS  기본 비교 = 최신 2건
2  PASS  지난 날짜 선택 → 26.4 - 23.9 = +2.5
...
7  FAIL  선택 날짜 삭제 후 NaN 표시
─────────────────────────────
PASS 9 / FAIL 1   (2026-08-25 14:20 KST)
```

`--json` 옵션으로 같은 결과를 `검사 기록/` 아래에 남겨, 작업 기록을 손으로 옮겨 적지 않게 한다.

## 3. 예산과 중단 계약 (카드 1)

작업 **시작 전에** 숫자로 정하고 커밋한다. 작업 중 유리한 쪽으로 바꾸지 않는다 — 바꾸면 `git log`에 남아 비교가 무효가 된다.

| 항목 | 단위 | AI A | AI B |
|------|------|------|------|
| 요청 상한 | 사람이 보낸 메시지 수 | 20 | 20 |
| 시간 상한 | 분 | 60 | 60 |
| 계획 중단 시점 | 아래 셋 중 **먼저 오는 것** | 요청 12회 / 45분 / 검사 6개 통과 | 상한 도달 또는 검사 10개 통과 |

**AI A가 상한 전에 다 끝내버리면?** 카드 2가 경고하는 상황이다. 그래서 중단 시점에 "검사 6개 통과"를 넣었다. 정상 4개 + 오류 1개까지가 AI A 몫, **오류 2개와 회귀 3개가 AI B 몫**이다. 회귀 검사를 AI B에게 남기는 것은 의도적이다 — 인계 문서가 "건드리면 안 되는 부분"을 제대로 전달했는지 검증하는 유일한 방법이기 때문이다.

**무료 한도 소진 방지** — 상한 20회는 두 환경 모두에서 무료 범위의 절반 이하다. 도달하면 그 자리에서 세션을 닫고 기록한다. 한도 초과 메시지를 보는 것 자체가 이 과제의 실패다.

## 4. 구조

과제 4의 구조는 그대로 두고, 새로 만드는 것만 표시한다.

```
today-dashboard/
├─ HANDOFF.md                     ★ 인계 문서 — 화면과 저장소가 공유하는 단 하나의 원본 (원칙 2)
├─ handoff/
│  └─ worklog.json                ★ 상한 · 두 AI 작업 기록 · 운영 기준
├─ tools/
│  ├─ capture.mjs
│  └─ check.mjs                   ★ 검사 10개 실행기 (원칙 1)
└─ src/
   ├─ core/
   │  ├─ computeDiff.js            (건드리지 않음 — 원칙 4)
   │  └─ selectPair.js            ★ 비교 기준 선택
   └─ components/
      ├─ DiffCard/                 (선택 표시 · 사유 문구 · 선택 해제 버튼 추가)
      ├─ HistoryList/              (행을 누를 수 있게 · 선택 표시)
      ├─ HandoffDoc/              ★ HANDOFF.md 를 화면에 렌더
      └─ WorklogTable/            ★ 두 AI 비교 표 + 운영 기준
```

**단일 원본 렌더링** (원칙 2) — 문서를 화면용으로 다시 쓰지 않는다.

```js
// components/HandoffDoc/index.jsx
import handoffText from "../../../HANDOFF.md?raw";
import worklog from "../../../handoff/worklog.json";
```

Vite의 `?raw`로 마크다운 원문을 그대로 읽어, `##` 제목과 `-` 목록만 처리하는 20줄짜리 렌더러로 그린다. 마크다운 라이브러리를 새로 넣지 않는다 — 이 과제에서 배울 것은 인계이고, 의존성 추가는 AI B의 실행 환경 재현을 어렵게 만든다.

## 5. 작업 기록 형식 (카드 2)

두 AI를 같은 단위로 비교하려면 **단위 정의가 작업 시작 전에 고정**돼야 한다. 나중에 정하면 유리한 쪽으로 해석된다.

| 항목 | 정의 | 근거 자료 |
|------|------|-----------|
| 시간 | 분. 첫 요청을 보낸 시각 ~ 마지막 응답을 받은 시각. 대기·휴식 제외 | 커밋 시각 |
| 요청 | **사람이 보낸 메시지 수.** AI 내부의 도구 호출은 세지 않음 | 대화 메시지 수 |
| 통과 검사 | `check.mjs`가 `PASS`로 찍은 번호 개수 | `검사 기록/*.json` |
| 남긴 오류 | 세션 종료 시점의 `FAIL` 번호 목록 | 같음 |
| 재작업 | 한 번 `PASS`였다가 다시 `FAIL`이 되어 **다시 실행한 검사 수** | 검사 기록 전후 비교 |
| 인계 이해 오류 | AI B가 인계 문서를 잘못 읽어 사람이 정정한 횟수 | `HANDOFF.md` 수정 전·후 diff |

```jsonc
// handoff/worklog.json
{
  "caps": { "requests": 20, "minutes": 60, "stopAt": "요청 12 / 45분 / 검사 6개 중 먼저" },
  "runs": [
    { "ai": "A", "model": null,          // ← 카드 5에서 기준을 확정한 뒤에 채운다
      "startCommit": "…", "endCommit": "…",
      "minutes": 0, "requests": 0,
      "passed": [], "failed": [], "rework": 0, "handoffMisreads": null,
      "note": "" },
    { "ai": "B", "model": null, "…": "…" }
  ],
  "criteria": []
}
```

`model`이 처음에 `null`인 것은 카드 5의 제목 그대로 **결과를 가리고 비교**하기 위한 것이다(§9).

## 6. AI A와 제한 안에서 작업 (카드 2)

1. **시작 상태를 커밋으로 고정한다.** `worklog.json`(상한 포함)과 검사 10개 목록, `check.mjs`를 먼저 커밋한다. 이 커밋이 "AI A 시작 상태"다.
2. **AI A에게 주는 것은 기능 문장 한 줄과 검사 10개 목록뿐이다.** 이 설계도를 그대로 붙여넣지 않는다 — 그러면 AI B와의 조건이 달라져 비교가 무효가 된다.
3. 변경마다 `node tools/check.mjs`를 돌리고, 누적 시간·요청·통과 번호·남은 오류·**내가 직접 고친 내용**을 한 줄씩 적는다.
4. 계획 중단 시점에 도달하면 **기능이 덜 끝난 상태로** 커밋하고 세션을 닫는다. 이 커밋이 "AI A 마지막 상태"다.

**화면에서 멈춘 지점이 보여야 한다** (카드 2 통과 기준). `WorklogTable`에서 AI A 행의 `passed`/`failed` 번호를 그대로 렌더한다 — 통과 6개는 초록 번호, 남은 4개는 회색 번호. "무엇이 끝났고 무엇이 남았는지"가 표 한 줄로 읽힌다.

## 7. 인계 문서 (카드 3)

`HANDOFF.md` **한 페이지**, 제목 7개 고정. 첫 대화를 보지 않은 사람이 이것만 읽고 이어갈 수 있어야 한다.

```markdown
# 인계 — 비교 기준 고르기

## 목표
사용자가 날짜별 기록 한 건을 누르면 그 날짜가 비교 기준이 되고 차이·방향·단위가 즉시 다시 계산된다.

## 현재 상태
- 바뀐 파일: src/core/selectPair.js (신규), src/components/DiffCard/index.jsx, src/components/HistoryList/index.jsx
- src/core/computeDiff.js 는 변경 없음
- 검사 6개 통과 / 4개 실패

## 실행 명령
cd today-dashboard
npm install
npm run dev            # http://localhost:5175
node tools/check.mjs   # 검사 10개, 번호별 PASS/FAIL 출력

## 통과한 검사
1, 2, 3, 4, 5, 9

## 남은 문제
- 6: 기록 1건일 때 행이 여전히 눌린다
- 7: 선택한 날짜를 지우면 차이에 NaN 이 뜬다
- 8: 장애 재현 후 선택 표시가 사라진다
- 10: 확인 안 됨

## 다음 행동
1. selectPair() 의 vanished 분기를 화면에 연결한다 (검사 7)
2. 기록 1건일 때 행 비활성 처리 (검사 6)
3. 장애 5종을 돌리고 선택 상태 유지 확인 (검사 8), 이어서 10 확인

## 건드리면 안 되는 부분
- src/core/computeDiff.js — 회귀 검사 8·9·10의 근거. 계산식을 옮기지 말 것
- storage/history.js 의 저장 키와 중복 방지 순서 — 과제 4의 통과 기준
- 선택 상태를 localStorage 에 저장하지 말 것 — 새로고침 시 기본 비교여야 함
```

**작성 규칙**

- 실행 명령은 **그대로 복사해 실행**할 수 있어야 한다. 작성 후 다른 폴더에서 클론해 한 번 실행해보고, 안 되면 문서를 고친다.
- 통과·실패는 반드시 **검사 10개의 번호**로 쓴다. "대충 잘 됨" 같은 표현을 쓰지 않는다.
- 비밀값·개인정보·첫 대화 전문을 넣지 않는다. AI 이름도 이 문서에는 쓰지 않는다.

## 8. AI B가 이어서 완성 (카드 4)

**새 대화창**에서 시작한다. 전달물은 셋뿐이다.

| 전달 | 금지 |
|------|------|
| 저장소(주소 또는 폴더) | 첫 대화 전문·요약·캡처 |
| `HANDOFF.md` | 이 설계도 |
| `node tools/check.mjs` 실행 결과 | 내 머릿속 배경 설명 |

**이해 확인 3질문** — 구현을 시작하기 전에 묻는다. 답이 틀리면 **코드를 고치지 말고 인계 문서를 먼저 고친다.**

1. 이 작업의 목표를 한 문장으로 말해보세요.
2. 지금 실패하는 검사 번호와 각각의 원인 추정은?
3. 건드리면 안 되는 파일은 무엇이고 왜인가요?

문서를 고친 **전·후 diff가 곧 `handoffMisreads`의 증빙**이다. 정정 횟수를 세어 `worklog.json`에 적는다.

변경마다 `check.mjs`를 돌린다. 회귀 3개(8·9·10)는 **매번** 함께 돌린다 — 원칙 4를 지켰는지 확인하는 유일한 장치다.

## 9. 결과를 가리고 비교 (카드 5)

**순서를 지킨다.** 모델 이름을 먼저 보면 기준이 인상평으로 오염된다.

1. 비교 표를 **A·B 익명 라벨로** 채운다 (근거는 §5의 자료뿐).
2. 검사 10개를 처음부터 다시 돌려 최종 결과를 기록한다.
3. 표만 보고 운영 기준 2~3개를 확정한다.
4. **그 다음에** `worklog.json`의 `model`을 채운다.

| 항목 | AI A | AI B |
|------|------|------|
| 시간 (분) | | |
| 요청 (사람 메시지 수) | | |
| 통과 검사 번호 | | |
| 남긴 오류 번호 | | |
| 재작업 (다시 실행한 검사 수) | | |
| 인계 이해 오류 (횟수) | | |

**운영 기준 문장 형식** — 측정칸을 직접 인용한다.

> `이런 작업에는 ______부터 사용하고, ______가 되면 바꾼다.`

예: "정해진 검사 목록을 채우는 작업은 요청당 통과 검사 수가 높은 쪽부터 쓰고, 같은 검사가 두 번 재작업되면 바꾼다." — 이 문장의 근거는 표의 `요청`과 `재작업` 칸이다. 모델 이름은 근거에 등장하지 않는다.

## 10. 화면 구성

개선 기능과 두 AI 비교가 **같은 화면**에 있어야 한다 (완료 기준 3). 별도 페이지로 나누지 않는다.

```
┌────────────────────────────────────────────────┐
│ 오늘의 진짜 정보판                                │
├────────────────────────────────────────────────┤
│ [CurrentValueCard]  값 · 단위 · 출처 · 조회 시각    │  (과제 4 그대로)
├────────────────────────────────────────────────┤
│ 비교 기준 고르기 — 아래 기록을 누르면 그 날짜와 비교  │ ★ 기능 이름 + 사용 방법
│ [DiffCard] 08-22 대비: ▲ +2.5 °C   [선택 해제]    │ ★
│           26.4 − 23.9 = 2.5                     │
├────────────────────────────────────────────────┤
│ [HistoryList]  ● 2026-08-24  26.4  직접 조회      │
```

`HandoffDoc`과 `WorklogTable`은 기본으로 접혀 있지 않다. 채점자가 15초 안에 판정하려면 스크롤만으로 닿아야 한다.

## 12. 검증 안내서 골격

> **어디로 가나요** — `https://aleph-dash.vercel.app` (설치·로그인 없음)
>
> **무엇을 하나요** (3단계)
> 1. `비교 기준 고르기` 아래 날짜별 기록에서 **아무 지난 날짜 한 건**을 누른다.
> 2. 바로 위 비교 줄의 날짜·차이·방향이 바뀌는지 본다.
> 3. 더 내려서 **인계 문서**와 **두 AI 비교 표**를 확인한다.
>
> **무엇이 보이면 통과인가요** — 누른 날짜가 비교 줄에 그대로 나타나고 차이·방향·단위가 즉시 바뀐다. 인계 문서에 제목 7개가 모두 있고, 두 AI 비교 표의 모든 칸이 같은 단위로 채워져 있으며 운영 기준 2~3개가 그 아래 있다.
>
> **안 될 때** — 기록이 1건뿐이면 `점검 도구 열기 → 지난 날짜 다시 불러오기`를 누른다. 최신 날짜를 누르면 비교가 안 되는 것이 정상이다(같은 날짜끼리는 비교하지 않는다). 선택을 되돌리려면 `선택 해제`를 누른다.
