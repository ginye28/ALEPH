## 한 줄 요약

WebAuthn은 자격증명이 클라우드에 백업된 상태인지(BS 플래그)를 매 인증마다 서비스에 알려 줍니다. 이 값은 시간이 지나면 바뀔 수 있어 등록 때 한 번 보는 것으로는 부족합니다. 실제로 배포된 시스템에서 백업 상태를 0에서 1로 바꿔 가며 30회 측정한 결과, **전송되는 플래그는 분명히 바뀌었지만, 서버의 응답은 10회 전부 완전히 같았고 보관 레코드도 로그인 횟수(`signCount`)를 빼면 완전히 같았습니다.** 동기화를 **끄는** 반대 방향에서도 결과는 대칭이었고, 이때 서버가 받는 바이트는 한 번도 백업된 적 없는 자격증명의 것과 같은 값이어서 두 상태를 구별할 수단 자체가 없었습니다. 다만 오픈소스 라이브러리 11개를 조사하니 이것이 보편적이지는 않았습니다 — 그중 4개는 규격대로 보관값을 대조하고 갱신합니다. 신호가 끊기는 곳은 라이브러리가 아니라 **라이브러리와 응용 사이**였고, 규격을 완전히 구현한 라이브러리 위에 서 있는 Spring Security와 Keycloak조차 신호를 잃고 있었습니다.

## 실험 A를 다시 돌려 보려면

측정 스크립트는 측정 대상 시스템(`portfolio-passkey`, 8번 과제 결과물)의 브라우저 하네스를 재사용하므로 **저장소 전체가 필요합니다.** 이 ZIP만으로는 실행되지 않습니다. 원자료는 이 ZIP 안에 그대로 들어 있으므로, 실행 없이 결과만 확인하려면 `원자료-*.json`을 열어 보면 됩니다.

저장소: https://github.com/ginye28/ALEPH (`10/` 폴더)

저장소 최상위에서 시작합니다. **창 두 개**가 필요합니다 — ①이 서버를 붙잡고 있기 때문입니다.

```bash
# ① 첫 번째 창: 측정 대상 서버를 띄운다 (창을 닫지 말 것)
cd 8/portfolio-passkey
npm install
npm run dev
# → "소개 페이지: http://localhost:5179" 이 뜨면 준비 완료

# ② 두 번째 창: 저장소 최상위에서 측정을 실행한다 (10회 반복)
node 10/측정-BE-BS.mjs http://localhost:5179 10

# ③ 공개 배포본으로 대조한다 (1회)
node 10/측정-BE-BS.mjs https://aleph-passkey.vercel.app 1
```

**Windows PowerShell 주의.** PowerShell 5.1(윈도우 기본)에서는 `&&`가 문 구분 기호가 아니므로 `cd A && npm run dev` 같은 한 줄 명령이 `'&&' 토큰은 이 버전에서 올바른 문 구분 기호가 아닙니다` 오류로 끝납니다. 위처럼 **줄을 나눠** 입력하거나, 굳이 한 줄로 쓰려면 `;`로 이으십시오(`cd 8/portfolio-passkey; npm run dev`). 또 ②·③의 `node 10/…`은 **저장소 최상위**에서 실행해야 합니다 — 홈 디렉터리에서 실행하면 `Cannot find module '...\10\측정-BE-BS.mjs'`가 납니다.

시나리오 3의 네 항목이 모두 `10/10`으로 나오면 논문의 결과가 재현된 것입니다. 자세한 통과 기준과 실패 시 화면은 `논문.md`의 부록 A에 있습니다.

**역전이(BS 1→0)** 까지 재려면 뒤에 `--역전이`를 붙입니다. 그러면 시나리오 4의 다섯 줄이 더 나오고, 다섯 항목 모두 `10/10`이면 논문 4.1절의 확장 측정이 재현된 것입니다. 플래그가 없으면 출력과 집계는 확장 이전과 완전히 같으므로 기존 결과 재현에는 영향이 없습니다.

`--상태변화` 플래그도 있습니다. 논문 5.4절이 한계로 적은 두 경우(상태를 여러 번 오가는 자격증명, 한 계정에 상태가 다른 자격증명 둘)를 재는 경로인데, **이 두 시나리오로 얻은 데이터는 논문에 없습니다** — 실행하려는 사람을 위해 경로만 만들어 둔 것입니다. 자세한 내용은 `논문.md` 부록 A.2에 있습니다.
