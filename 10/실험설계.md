# 실험 설계 — 데이터 수집 이전에 확정한 조건

**확정 일시**: 2026-09-10 (데이터 수집 착수 전)
**원칙**: 이 문서를 먼저 고정한 뒤 수집을 시작한다. 수집 도중 설계를 바꾸게 되면 지우지 않고 변경 이력(§5)에 추가한다.

---

## 1. 가설

> **자격증명의 백업 상태(BS)가 "기기 전용"에서 "클라우드 동기화"로 전이해도, WebAuthn 표준을 정석대로 따른 RP 구현에서는 서버의 응답과 저장 상태가 달라지지 않는다.**

- **원인(독립변수)**: 자격증명의 백업 상태 전이 (BS: 0 → 1)
- **결과(종속변수)**: RP의 관측 가능한 반응 — 응답 본문, 저장된 자격증명 레코드, 부가 동작(재인증 요구·사용자 알림)
- **가설의 방향**: "영향을 주지 않는다"(귀무가설형). 즉 전이가 일어나도 RP 쪽에는 아무 변화가 없다.

### 가설이 틀렸다면 나올 결과 (기각 조건)

다음 중 **하나라도** 관측되면 가설은 기각된다.

- (R1) BS 전이 전후의 로그인 응답 본문이 서로 다르다.
- (R2) 전이 후 서버가 저장한 자격증명 레코드에 변화가 생긴다(필드 추가·값 변경).
- (R3) 전이가 재인증 요구, 경고 표시, 로그 기록 등 별도 동작을 유발한다.
- (R4) 조사 대상 구현체 다수가 등록 시 BE/BS를 저장하고 인증 시 재확인한다.

---

## 2. 실험 A — 단일 시스템 동적 측정

실제로 배포·운영 중인 RP 하나를 대상으로, 인증장치 계층을 직접 제어하며 RP의 반응을 관측한다.

| 구분 | 내용 |
|---|---|
| **대상** | `portfolio-passkey` (필자 구현, `@simplewebauthn/server` v13.3.3) |
| **바꾸는 조건** | 가상 authenticator의 BE/BS 설정값, 그리고 등록 이후의 BS 전이 여부 |
| **고정하는 조건** | RP 코드·버전, 인증장치의 나머지 성질(`protocol: ctap2`, `transport: internal`, `hasResidentKey: true`, `hasUserVerification: true`, `isUserVerified: true`), 브라우저(헤드리스 Chrome), 요청 흐름(등록 → 로그인) |
| **조건 수** | 3가지 시나리오 — ① BE=1·BS=1(동기화), ② BE=0·BS=0(기기 전용), ③ BE=1·BS=0 → BS=1(전이) |
| **반복 횟수** | 각 시나리오 **10회**, 총 30회 |
| **측정값** | (a) 기기가 전송한 authenticatorData 33번째 바이트(플래그)의 정수·16진값과 UP/UV/BE/BS 비트, (b) 등록 응답의 `credentialDeviceType`·`backedUp`, (c) 로그인 응답 본문 전문, (d) 전이 전후 서버가 보관 중인 자격증명 레코드 전문 |
| **판정 기준** | 시나리오 ③에서 전이 전후의 (c)와 (d)가 완전히 일치하면 그 회차는 "변화 없음"으로 기록. 10회 중 단 한 번이라도 달라지면 R1·R2에 해당 |
| **실행 환경** | 로컬 개발 서버(`tools/dev-server.mjs`). 반복 측정이 공개 배포본의 데이터베이스에 30개 계정을 만들지 않도록 하고, 신규 계정 속도 제한(10분당 20회)에 걸리지 않게 하기 위함 |
| **보조 확인** | 공개 배포본(`https://aleph-passkey.vercel.app`)에 대해 각 시나리오 1회씩 별도 측정하여 로컬 결과와 일치하는지 대조 |

## 3. 실험 B — 오픈소스 구현체 횡단 조사

실험 A가 단일 사례이므로, 같은 현상이 다른 구현에서도 나타나는지 조사한다.

| 구분 | 내용 |
|---|---|
| **모집단** | 서버 측 WebAuthn 검증을 수행하는 공개 오픈소스 구현체 |
| **표본 선정 기준** | (a) 서버 측 등록·인증 검증을 직접 수행할 것, (b) 소스가 공개되어 확인 가능할 것, (c) 서로 다른 언어·생태계를 포함할 것, (d) 실제로 사용되는 프로젝트일 것 |
| **표본 수** | **10개** (목표). 기준을 못 채워 제외한 것이 있으면 이유와 함께 기록한다 |
| **바꾸는 조건** | 구현체(언어·라이브러리) |
| **고정하는 조건** | 조사 항목(아래 M1–M4), 조사 시점(2026-09-10), 판정 방식(공개 소스와 공식 예제·문서만 근거로 삼음) |
| **측정값** | 구현체별로 다음 네 항목을 예/아니오/해당없음으로 판정 |

- **M1** — 라이브러리가 **등록** 검증 결과에서 BE/BS(또는 그에 대응하는 값)를 호출자에게 노출하는가?
- **M2** — 라이브러리가 **인증** 검증 결과에서 BE/BS를 호출자에게 노출하는가?
- **M3** — 공식 예제·데모 서버가 등록 시 그 값을 **저장**하는가?
- **M4** — 공식 예제·데모 서버가 인증 시 그 값을 **재확인·갱신**하는가?

**기록 방식**: 구현체명, 확인한 버전 또는 커밋, 근거가 된 파일 경로와 행 번호, 확인 날짜, 판정 근거가 되는 인용문.

**판정 원칙**: 소스에서 직접 확인되지 않은 것은 "확인 불가"로 적고 예/아니오로 밀어 넣지 않는다. M3·M4는 공식 예제가 없으면 "해당 없음"으로 둔다.

---

## 4. 이 설계로 말할 수 없는 것 (사전 기록)

- 실험 B는 **정적 조사**이므로 "예제가 저장하지 않는다"는 것이 "그 라이브러리를 쓴 실제 서비스가 저장하지 않는다"를 뜻하지는 않는다. 각 서비스는 예제를 그대로 쓰지 않는다.
- 실험 A의 가상 authenticator는 플래그를 그렇게 **신고**할 뿐 실제 클라우드 동기화를 수행하지 않는다. 관측 대상이 RP의 처리 방식이므로 결론에는 영향이 없으나, 플랫폼 제공자 측 동작을 검증한 것은 아니다.
- 두 실험 모두 공격의 성공 여부가 아니라 **RP의 관측 능력**을 측정한다.

---

## 5. 설계 변경 이력

수집 도중 설계를 바꾸게 되면 여기에 시각·내용·이유를 추가한다. 바꾸기 전 데이터는 지우지 않는다.

| 시각 | 바꾼 것 | 이유 |
|---|---|---|
| 2026-09-10 (예비 측정 단계) | 서버 보관 상태 조회 경로를 `/api/credentials` → `/api/me`로 정정 | 예비 측정에서 `/api/credentials`가 빈 객체를 반환. 확인 결과 해당 경로에는 GET 핸들러가 없고 자격증명 목록은 `/api/me`가 내려주는 구조였음. 측정 대상 값을 바꾼 것이 아니라 같은 값을 올바른 경로에서 읽도록 고친 것 |
