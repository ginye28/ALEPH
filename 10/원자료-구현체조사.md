# 원자료 — 오픈소스 WebAuthn 구현체 횡단 조사 (실험 B)

**조사일**: 2026-09-10
**조사 방법**: 각 구현체의 공개 소스(GitHub raw 파일) 및 공식 API 문서를 직접 열람. 2차 해설 글은 근거로 삼지 않으며, 소스에서 확인되지 않은 항목은 "확인 불가"로 적는다.
**표본 수**: 10개 (설계서 §3의 목표치와 일치)

## 측정 항목

- **M1** — 라이브러리가 **등록** 검증 결과에서 BE/BS를 호출자에게 노출하는가
- **M2** — 라이브러리가 **인증** 검증 결과에서 BE/BS를 호출자에게 노출하는가
- **M3** — 기본 저장 모델 또는 공식 예제가 그 값을 **저장**하는가
- **M4** — 인증 시 그 값을 **재확인·갱신**하는가

> **정의 변경 고지.** M3·M4는 설계서 §3의 원문("공식 예제·데모 서버가 …")을 조사 착수 후 넓힌 것이다. 예제와 무관하게 저장 모델 자체에 값을 넣어 둔 프레임워크와 라이브러리가 직접 갱신하는 구현을 놓치지 않기 위해서다. 이 확장은 저장·갱신하는 구현을 더 많이 잡아내므로 가설에 불리한 방향이며, 경위는 `실험설계.md` §5와 `논문.md` 3.5절에 기록했다.

|---|---|---|
| M1 | **아니오** | `lib/parser.js`의 플래그 파싱이 BE·BS 비트를 예약 비트로 취급 |
| M2 | **아니오** | 위와 같음 |

해당 코드:

```javascript
if (flags & 0x01) flagsSet.add("UP");
if (flags & 0x02) flagsSet.add("RFU1");
if (flags & 0x04) flagsSet.add("UV");
if (flags & 0x08) flagsSet.add("RFU3");   // ← BE 비트
if (flags & 0x10) flagsSet.add("RFU4");   // ← BS 비트
if (flags & 0x20) flagsSet.add("RFU5");
if (flags & 0x40) flagsSet.add("AT");
if (flags & 0x80) flagsSet.add("ED");
```

WebAuthn Level 3 기준으로 `0x08`은 BE, `0x10`은 BS이나 이 구현은 둘 다 RFU(예약)로 이름 붙여 두었다. **신호가 개발자에게 도달조차 하지 않는 유일한 사례.**

# 2차 조사 (2026-09-11) — 재조사 정정과 표본 확대

**왜 다시 했나.** 1차 조사(2026-09-10)는 공개 문서와 Javadoc을 주로 보았고, 소스에서 확인되지 않은 항목을 "확인 불가"로 남겼다(M3 2칸, M4 4칸 등 40칸 중 8칸). 논문을 후속 과제의 토대로 쓰기로 하면서, 그 미판정 칸이 결론의 핵심 숫자("규격이 권고했는데 구현한 것은 소수")를 떠받치고 있다는 점이 문제가 되었다. 미판정을 근거 삼아 "소수"라고 말할 수는 없다. 그래서 **각 저장소를 내려받아 소스를 직접 읽었다.**

**방법.** `git clone --depth 1` 로 저장소를 받아 검증 경로와 자격증명 모델을 직접 열람했다. 1차 조사의 판정은 **지우지 않고** 아래에 정정 이력으로 남긴다.

## 2-1. 재조사로 정정된 판정 — 3건

세 건 모두 **1차 조사가 과소평가한 쪽**이다. 즉 정정은 논문의 원래 주장에 불리한 방향이다.

| 구현체 | 1차 판정 (09-10) | 2차 판정 (09-11) | 정정 근거 (직접 읽은 소스) |
|---|---|---|---|
| **webauthn-rs** | M3 확인 불가 · M4 확인 불가 | **M3 예 · M4 예** | `webauthn-rs-core/src/interface.rs`의 `Credential` 구조체에 `backup_eligible: bool`·`backup_state: bool` 필드가 있고, `webauthn-rs/src/interface.rs`의 `update_credential()`이 매 인증마다 `if res.backup_state() != self.cred.backup_state { self.cred.backup_state = res.backup_state(); changed = true; }` 로 갱신한다. BE는 거짓→참 방향으로만 올린다 |
| **webauthn4j** | M1·M2 예(간접) · M3 확인 불가 · M4 확인 불가 | **M1·M2 예 · M3 예 · M4 예** | `credential/CoreCredentialRecord.java`가 `isBackupEligible()`·`isBackedUp()`·`setBackedUp(boolean)`을 인터페이스로 정의한다. `verifier/AuthenticationDataVerifier.updateRecord()`가 매 인증마다 `coreCredentialRecord.setBackedUp(authenticatorData.isFlagBS())`를 호출하고, 전용 클래스 `verifier/internal/BEFlagVerifier.java`가 보관된 BE와 현재 BE를 대조해 어긋나면 `BadBackupEligibleFlagException`을 던진다 |

**이 정정의 의미.** 1차 조사의 "확인 불가"는 소스를 안 읽고 문서만 본 결과였고, 실제로는 세 구현 모두 규격의 저장·대조·갱신 모델을 구현하고 있었다. 따라서 1차 조사에 근거한 "구현한 것은 많아야 2개"라는 서술은 **사실이 아니다**. 논문 4.2·4.3·6장의 해당 서술을 2차 조사에 맞춰 고쳤다.

## 2-3. 새 조사 축 — 라이브러리를 쓰는 응용은 어떻게 하는가

2-1의 정정으로 "라이브러리는 대체로 규격을 따라잡았다"가 분명해지자, 질문이 한 칸 옮겨갔다 — **그렇다면 그 라이브러리를 쓰는 응용은?** 마침 1차 조사의 두 표본이 같은 라이브러리(webauthn4j) 위에 서 있어 직접 비교가 가능했다.

### A. Spring Security WebAuthn (webauthn4j 위)

| 단계 | 무엇을 하는가 | 근거 |
|---|---|---|
| 등록 | **BE/BS를 저장한다** | `Webauthn4JRelyingPartyOperations.java` 292–293행 `.backupEligible(wa4jAuthData.isFlagBE()).backupState(wa4jAuthData.isFlagBS())`. `JdbcUserCredentialRepository.java`가 `backup_eligible`·`backup_state` 컬럼으로 영속화(226·231·307·310행) |
| 인증 | **갱신하지 않는다** | 같은 파일 418–423행. 인증 후 만드는 `updatedRecord`는 `.lastUsed(...)` 와 `.signatureCount(updatedSignCount)` 만 바꾸고 `backupState`는 이전 레코드 값을 그대로 복사한다 |
| 인증 | **보관값을 라이브러리에 넘기지도 않는다** | 405–407행. webauthn4j에 건네는 `new CredentialRecordImpl(wa4jAttestationObject, null, null, transports)` 에는 보관된 BE/BS가 들어 있지 않다. 그 결과 webauthn4j의 `BEFlagVerifier`는 `isBackupEligible()`이 null이 되어 **no-op으로 통과한다** |

**즉 Spring Security는 규격의 대조 단계를 구현한 라이브러리를 쓰면서, 그 단계가 작동하지 않도록 호출한다.** 저장은 하는데 읽지 않고, 읽지 않으니 갱신도 하지 않는다.

### B. Keycloak (webauthn4j 위)

| 단계 | 무엇을 하는가 | 근거 |
|---|---|---|
| 저장 | **필드 자체가 없다** | `server-spi/.../dto/WebAuthnCredentialData.java`가 담는 값: `aaguid, credentialId, attestationStatement, credentialPublicKey, counter, attestationStatementFormat, transports`. 백업 관련 필드 없음 |
| 인증 | **라이브러리 로직이 우회된다** | `services/.../WebAuthnCredentialProvider.java` 222행이 `new AuthenticatorImpl(...)` 을 쓴다. webauthn4j의 `AuthenticatorImpl`은 `CoreAuthenticatorImpl implements Authenticator` 이며 **`CoreCredentialRecord`가 아니다.** `BEFlagVerifier.verify()`와 `updateRecord()`는 둘 다 `if (authenticator instanceof CoreCredentialRecord)` 로 진입하므로, Keycloak 경로에서는 **조용히 건너뛴다** |
| 전체 | 저장소 전역에 BE/BS 없음 | `grep -rn "isFlagBE\|isFlagBS\|BackupEligible\|backupState\|isBackedUp" --include=*.java .` → 0건 |

### C. portfolio-passkey (SimpleWebAuthn 위) — 실험 A의 측정 대상

라이브러리는 매 인증마다 `credentialBackedUp`을 계산해 반환하지만(논문 4.1절), 응용은 그 값을 꺼내지 않고 스키마에 컬럼도 없다. **공식 예제가 저장하지 않는 구조를 그대로 따랐다.**

### 이 축의 집계

| 응용 | 기반 라이브러리 | 그 라이브러리의 M4 | 응용이 신호를 지키는가 |
|---|---|---|---|
| Spring Security WebAuthn | webauthn4j | **예** | **아니오** (저장하되 갱신·대조 안 함) |
| Keycloak | webauthn4j | **예** | **아니오** (저장 필드 없음, 라이브러리 로직 우회) |
| portfolio-passkey | SimpleWebAuthn | 아니오 | **아니오** (공식 예제를 따름) |

**조사한 응용 3개 모두 신호를 잃었다. 그중 둘은 규격을 완전히 구현한 라이브러리 위에 서 있다.**
