## 초록

FIDO2/WebAuthn은 개인키가 인증장치를 벗어나지 않는다는 전제 위에서 피싱 저항성을 확보해 왔다. 그러나 애플·구글 등 플랫폼 사업자가 개인키를 클라우드 계정에 종단간 암호화로 동기화하는 "동기화 패스키(synced passkey)"를 표준 경로로 채택하면서, 이 전제는 더 이상 모든 패스키에 보편적으로 성립하지 않는다. 본 연구는 새로운 인증 게이트웨이를 설계하거나 그 성능을 측정하는 대신, WebAuthn 표준이 이미 정의하고 있는 Backup Eligibility(BE)·Backup State(BS) 플래그를 축으로 동기화 패스키 도입이 FIDO2 위협모델의 전제를 어떻게 바꾸는지 재검토한다. 구체적으로는 클라우드 계정 탈취를 통한 간접적 크리덴셜 노출, 계정 복구·기기 이관 흐름에서의 공격 벡터, RP(서비스 제공자)가 더 이상 "하드웨어 격리 여부"를 검증 시점 이후로는 추적할 수 없는 문제를 다룬다. 사례 분석으로 필자가 직접 구현한 패스키 기반 인증 시스템(`portfolio-passkey`)의 실제 서버 코드를 검토한 결과, 라이브러리가 등록 시점에 BE/BS에 해당하는 값을 이미 계산해 응답에 담고 있음에도 이를 데이터베이스에 저장하지 않고, 로그인 시점에는 아예 다시 확인하지 않는다는 사실을 확인했다. 이는 이 시스템에 국한된 문제가 아니라, BE/BS 플래그를 표준이 제공함에도 실무에서 활용하지 않을 때 생기는 전형적인 사각지대임을 보여준다. 이를 근거로 RP 관점의 완화 방안을 제시한다.

**키워드**: FIDO2, WebAuthn, 패스키, 동기화 패스키, Backup Eligibility, Backup State, 위협모델, 계정 탈취

## 1. 서론

### 1.1 연구 배경

비밀번호는 재사용·피싱·크리덴셜 스터핑에 구조적으로 취약하다는 문제가 오랫동안 지적되어 왔고, 그 대안으로 FIDO 얼라이언스와 W3C가 공동 표준화한 FIDO2(WebAuthn + CTAP)가 애플·구글·마이크로소프트 등 주요 플랫폼에 채택되며 "패스키(passkey)"라는 이름으로 소비자 서비스에 빠르게 확산되고 있다.

### 1.2 문제 제기

FIDO2가 비밀번호 대비 확보한 피싱 저항성의 근거는 "공개키 암호 쌍의 개인키가 인증장치(authenticator) 밖으로 절대 나가지 않는다"는 전제였다. 그런데 사용자 편의를 위해 애플의 iCloud 키체인, 구글의 비밀번호 관리자 등은 이 개인키 자체를 사업자의 클라우드 계정에 종단간 암호화 형태로 동기화해 여러 기기에서 같은 패스키를 쓸 수 있게 한다. 이 방식은 편의성 면에서는 명백한 개선이지만, "개인키가 기기를 벗어나지 않는다"는 원래의 전제를 사실상 "개인키가 클라우드 계정 밖으로 나가지 않는다"로 바꿔 놓는다. 즉 위협의 경계가 기기 하나에서 사용자의 클라우드 계정 전체로 확장된다.

### 1.3 연구 목적 및 범위

본 연구는 새로운 프로토콜이나 게이트웨이 아키텍처를 제안하지 않는다. 대신 WebAuthn 표준이 이미 규정하고 있는 BE(Backup Eligible)·BS(Backup State) 플래그를 실마리로,
1. 동기화 패스키 도입이 기존 FIDO2 위협모델의 어느 전제를 무너뜨리는지,
2. 그 결과 RP가 실무에서 놓치기 쉬운 지점이 무엇인지를

필자가 실제로 구현·배포한 패스키 인증 시스템의 서버 코드를 사례로 삼아 검토한다. 성능(지연시간·처리량) 비교는 본 연구의 범위 밖이다.

## 2. 배경 및 관련 개념

### 2.1 FIDO2/WebAuthn 인증 구조와 원래의 위협모델

WebAuthn 등록(registration) 시 인증장치는 공개키·개인키 쌍을 생성하고 공개키만 RP 서버에 전달한다. 인증(authentication) 시에는 서버가 보낸 일회용 challenge에 개인키로 서명해 응답하며, 서버는 저장해 둔 공개키로 이를 검증한다. 개인키가 인증장치 밖으로 나간 적이 없으므로, 서버(RP)가 탈취당하거나 통신 구간이 도청되어도 개인키 자체는 노출되지 않는다 — 이것이 비밀번호·OTP 대비 FIDO2가 갖는 근본적 강점이다.

### 2.2 동기화 패스키의 등장 배경과 구현 방식

애플은 iCloud 키체인을 통해, 구글은 구글 비밀번호 관리자를 통해 패스키의 개인키를 사용자의 클라우드 계정에 종단간 암호화로 동기화한다. 사업자 측 설명에 따르면 서버는 암호화된 상태의 키만 보관하고 복호화 키는 사용자의 기기·계정 자격증명에서 파생되므로, 사업자가 직접 개인키를 열람할 수는 없다고 알려져 있다. 그러나 이 구조가 성립하려면 "사용자의 클라우드 계정 자체가 안전하다"는 새로운 전제가 필요하며, 이 전제는 기존 FIDO2 위협모델에는 없던 것이다.

### 2.3 Backup Eligibility(BE)/Backup State(BS) 플래그

WebAuthn의 `authenticatorData` 구조체에는 1바이트의 flags 필드가 있고, 그중 두 비트가 각각 다음을 의미한다.

| 비트 | 이름 | 의미 |
|---|---|---|
| bit 0 (0x01) | UP | User Present — 사용자가 물리적으로 조작(터치 등)했는가 |
| bit 2 (0x04) | UV | User Verified — 생체인식·PIN 등으로 사용자를 확인했는가 |
| bit 3 (0x08) | **BE** | Backup Eligible — 이 자격증명이 애초에 백업(동기화) 가능한 종류로 만들어졌는가 |
| bit 4 (0x10) | **BS** | Backup State — 지금 실제로 백업(동기화)된 상태인가 |
| bit 6 (0x40) | AT | 첨부된 자격증명 데이터 포함 여부 |

BE가 0이면 그 자격증명은 태생부터 기기 밖으로 나갈 수 없는 하드웨어 바운드 자격증명(예: 보안키, TPM 기반 플랫폼 인증장치)이고, BE가 1이면 클라우드 동기화가 가능한 종류다. BS는 그중 "지금 실제로 동기화가 완료된 상태인지"를 나타낸다 — 예를 들어 BE=1이어도 사용자가 동기화 기능을 아직 켜지 않았다면 BS=0일 수 있다. 이 두 비트는 등록 응답뿐 아니라 매 인증(로그인) 응답에도 실려 온다는 점이 본 연구의 4장에서 핵심적으로 다뤄진다.

## 3. 위협모델 재검토: 공격 표면 분석

### 3.1 기존 FIDO2 위협모델의 전제와 그 한계

기존 위협모델은 "공격자가 RP 서버, 통신 구간, 심지어 사용자의 비밀번호를 모두 손에 넣어도 개인키는 얻을 수 없다"는 것을 핵심 방어선으로 삼았다. 이 전제는 BE=0인 하드웨어 바운드 자격증명에는 여전히 유효하다. 그러나 BE=1인 동기화 패스키에서는 "개인키를 얻을 수 있는 경로"가 하나 늘어난다 — 바로 사용자의 클라우드 계정이다.

### 3.2 클라우드 계정 탈취를 통한 간접 크리덴셜 노출 시나리오

공격자가 사용자의 애플/구글 계정을 다른 경로(예: 계정 자체의 비밀번호 재사용, 계정 복구 절차 악용, 세션 토큰 탈취)로 장악하면, 그 계정에 동기화된 모든 패스키의 개인키에 접근할 수 있는 조건이 갖춰진다. 즉 서비스 하나하나를 개별적으로 공격할 필요 없이, 클라우드 계정 하나만 뚫으면 그 계정에 연결된 모든 서비스의 패스키가 한꺼번에 위험해지는 구조로 바뀐다. 이는 기존에 개별 서비스 단위로 흩어져 있던 위험을 클라우드 계정이라는 단일 지점으로 집중시키는 효과를 낳는다.

### 3.3 계정 복구·기기 이관 흐름에서의 공격 벡터

패스키의 강점 중 하나로 흔히 "탈취할 비밀번호 자체가 없다"는 점이 꼽히지만, 이는 정상적인 로그인 경로에 한정된 이야기다. 사용자가 기기를 분실하거나 교체할 때 거치는 클라우드 계정의 자체 복구 절차(이메일 인증, SMS, 보안 질문 등)는 여전히 전통적인 인증 수단에 의존하는 경우가 많다. 이 복구 절차가 뚫리면 공격자는 패스키 자체를 위조할 필요 없이, 클라우드 계정에 로그인해 동기화된 패스키를 그대로 자신의 기기에서 사용할 수 있게 된다. 즉 공격의 무게중심이 "패스키를 직접 공격하는 것"에서 "패스키를 보관하는 계정의 복구 절차를 공격하는 것"으로 옮겨간다.

### 3.4 Attestation 신뢰 저하 문제

WebAuthn은 등록 시 attestation(증명)을 통해 RP가 "이 자격증명이 어떤 종류의 인증장치에서 만들어졌는지"를 암호학적으로 검증할 수 있는 장치를 두고 있다. 그러나 플랫폼 인증장치 대부분은 프라이버시 보호를 이유로 `none`에 가까운 약한 attestation conveyance를 기본값으로 쓰거나, 개별 기기를 특정할 수 없도록 익명화된 attestation을 제공한다. 그 결과 RP는 attestation만으로는 "이 자격증명이 하드�어에 격리되어 있는지"를 신뢰성 있게 구분하기 어렵고, 사실상 BE/BS 플래그 — 즉 인증장치(또는 그 뒤의 OS)가 스스로 보고하는 값 — 에 의존하게 된다. 이는 이 플래그들이 RP가 독립적으로 검증할 수 있는 암호학적 증거가 아니라, 신뢰하는 플랫폼의 자기 보고(self-report)라는 한계를 갖는다는 뜻이기도 하다.

### 3.5 하드웨어 바운드 패스키 vs 동기화 패스키 비교

| 항목 | 하드웨어 바운드 (BE=0) | 동기화 패스키 (BE=1) |
|---|---|---|
| 개인키 존재 범위 | 물리적 인증장치 1개 | 사용자의 클라우드 계정(여러 기기) |
| 기기 분실 시 영향 | 그 기기의 자격증명만 무효화하면 됨 | 클라우드 계정이 살아 있으면 다른 기기에서 계속 사용 가능(복구 관점에서는 장점) |
| 클라우드 계정 탈취 시 영향 | 영향 없음 | 동기화된 모든 서비스의 패스키가 잠재적으로 노출 |
| RP의 검증 가능성 | attestation으로 비교적 신뢰 가능 | BE/BS 자기 보고 값에 의존 |
| 복구 절차 의존도 | 낮음(분실 시 재등록 필요) | 높음(클라우드 계정 복구 절차가 사실상의 신뢰 기반) |

## 4. 사례 분석: 자체 구현 시스템(portfolio-passkey)을 통한 검증

### 4.1 시스템 개요 및 등록·인증 흐름 요약

`portfolio-passkey`는 필자가 직접 설계·구현한 패스키 전용 인증 시스템으로, 서버는 `@simplewebauthn/server` 라이브러리로 등록·인증 응답을 검증하고, Vercel 서버리스 함수 위에서 동작하며 Neon Postgres에 자격증명을 저장한다. 등록 흐름은 다음과 같다.

1. 클라이언트가 등록 옵션을 요청 → 서버가 challenge 발급 (`api/register/options.js`)
2. 브라우저의 WebAuthn API가 인증장치에 자격증명 생성을 요청
3. 브라우저가 만들어진 공개키·attestation을 서버로 전송 → 서버가 `verifyRegistrationResponse`로 검증 (`api/register/verify.js`)

### 4.2 등록 단계에서 BE/BS에 해당하는 값의 실측 확인

`api/register/verify.js`의 실제 코드를 보면, `verifyRegistrationResponse`가 반환하는 `registrationInfo` 안에 이미 `credentialDeviceType`(BE에 대응 — `"singleDevice"` 또는 `"multiDevice"`)와 `credentialBackedUp`(BS에 대응 — boolean)이 계산되어 들어 있다.

```js
// api/register/verify.js, 63번째 줄
const { credential, credentialDeviceType, credentialBackedUp } = verification.registrationInfo;
```

그리고 이 값은 실제로 API 응답에도 그대로 실려 나간다.

```js
// api/register/verify.js, 95~103번째 줄
sendJson(res, 200, {
    ok: true,
    credentialId: credential.id,
    deviceName: pending.device_name,
    newAccount: pending.is_new_account,
    // 기기가 이 패스키를 다른 기기와 동기화하는 종류인지(구글/애플 비밀번호 관리자 등) — T08-C26
    credentialDeviceType,
    backedUp: credentialBackedUp,
});
```

**실측 방법(제출 전 직접 수행)**: 브라우저 개발자 도구의 네트워크 탭을 열어 두고, (a) 동기화가 켜진 플랫폼 인증장치(예: 데스크톱 크롬 + 구글 비밀번호 관리자, 또는 아이폰 Face ID)로 한 번, (b) 하드웨어 보안키(예: YubiKey) 또는 동기화가 꺼진 Windows Hello로 한 번, 각각 새로 회원가입을 진행하면서 `/api/register/verify` 응답 바디의 `credentialDeviceType`·`backedUp` 값을 그대로 기록한다.

| 인증장치 종류 | credentialDeviceType | backedUp | 비고 |
|---|---|---|---|
| 동기화 플랫폼 인증장치 (예: 크롬+구글 비밀번호 관리자) | `[실측값 입력]` | `[실측값 입력]` | |
| 하드웨어 보안키 / 동기화 미사용 | `[실측값 입력]` | `[실측값 입력]` | |

### 4.3 관찰 결과 — 노출되는 지점과 이미 방어되고 있는 지점

코드를 근거로 확인한 사실은 다음과 같다.

- **이미 방어되고 있는 지점**: 개인키 자체는 등록·인증 어느 시점에도 서버로 전송되지 않는다(WebAuthn 규격상 애초에 그런 필드가 없다). 서버가 저장하는 것은 공개키뿐이며, 이는 동기화 패스키 여부와 무관하게 항상 성립한다.
- **놓치고 있는 지점 ①**: `credentialDeviceType`/`credentialBackedUp`은 등록 시점에 이미 계산되어 응답까지 나가지만, `pk_credentials` 테이블(`db/schema.sql` 20~28번째 줄)에는 이를 저장할 칸이 없다. 그 결과 이 값은 등록 순간의 UI 표시(예: "이 패스키는 다른 기기와 동기화됩니다" 배지)에만 쓰이고, 이후 감사·정책 판단에는 전혀 활용되지 못한 채 사라진다.
- **놓치고 있는 지점 ②**: `api/login/verify.js`는 `verifyAuthenticationResponse`가 반환하는 `authenticationInfo`에서 `newCounter`만 꺼내 쓰고(79~83번째 줄), 같은 객체 안에 있는 `credentialDeviceType`/`credentialBackedUp`은 아예 읽지 않는다. 즉 이 시스템은 로그인이 일어날 때마다 실려 오는 BE/BS 값을 매번 그냥 버리고 있다.
- **왜 문제인가**: BE는 자격증명이 생성될 때 정해져 바뀌지 않지만, BS는 시간이 지나면서 바뀔 수 있다 — 예를 들어 등록 시점에는 동기화가 꺼져 있었더라도(BS=0) 사용자가 나중에 클라우드 동기화를 켜면 그 다음 로그인부터 BS=1로 바뀐다. 등록 시점만 확인하고 이후로는 다시 확인하지 않는 현재 구조에서는, "처음에는 기기 하나에만 있던 패스키가 어느 순간부터 클라우드 계정에도 존재하게 되었다"는 위험모델의 변화를 RP가 전혀 알아채지 못한다.

이는 `portfolio-passkey`만의 결함이 아니라, BE/BS라는 신호를 표준이 이미 제공하고 있음에도 실무 구현에서는 등록 시점의 UI 표시용으로만 소비되고 지속적인 보안 신호로는 취급되지 않는 전형적인 패턴을 보여주는 사례로 제시한다.

## 5. 완화 방안 및 설계 제언

### 5.1 RP 관점의 정책적 대응

- **BE/BS 지속 기록**: 등록 시점의 `credentialDeviceType`·`credentialBackedUp`을 `pk_credentials`에 컬럼으로 추가해 저장하고, 이후 매 로그인마다 `authenticationInfo`의 같은 값을 다시 확인해 변경 여부를 갱신한다. BS가 0→1로 바뀌는 시점을 포착하면 "이 패스키가 방금 클라우드 동기화를 시작했다"는 것을 알 수 있다.
- **위험 기반 재인증**: BS가 0에서 1로 바뀐 직후, 혹은 새로운 기기에서 이미 BS=1인 자격증명으로 처음 로그인하는 경우, 민감한 작업(비공개 자료 열람, 패스키 삭제 등)에 대해서는 재인증을 한 번 더 요구한다. 이는 `portfolio-passkey`가 이미 갖추고 있는 `reauth_at` 기반 재확인 장치(`db/schema.sql` 57~60번째 줄)를 BE/BS 신호로 트리거하도록 확장하는 방향이다.

### 5.2 하드웨어 바운드 패스키를 선택적으로 요구하는 방안

보안 민감도가 높은 서비스(금융, 관리자 계정 등)는 등록 시점에 `authenticatorSelection`의 조건을 강화해 BE=0인 자격증명만 허용하거나, BE=1인 자격증명 등록 시 사용자에게 그 의미(클라우드 계정이 곧 신뢰 경계가 됨)를 명시적으로 고지하는 방안을 고려할 수 있다.

### 5.3 향후 표준·생태계 변화 전망

FIDO 얼라이언스와 플랫폼 사업자들은 동기화 패스키의 편의성과 하드웨어 바운드 패스키의 보안성 사이의 격차를 줄이기 위한 논의를 계속하고 있는 것으로 알려져 있다. RP 입장에서는 어느 한쪽이 "표준 해법"으로 정리되기를 기다리기보다, 지금 표준이 이미 제공하는 BE/BS 신호부터 최대한 활용하는 것이 현실적인 대응이다.

## 6. 결론

### 6.1 연구 요약

동기화 패스키의 확산은 FIDO2가 원래 전제했던 "개인키는 기기를 벗어나지 않는다"는 명제를 "개인키는 클라우드 계정을 벗어나지 않는다"로 바꾸어 놓았다. 이는 위협의 경계를 기기 단위에서 계정 단위로 확장시키며, 클라우드 계정 탈취·복구 절차 악용·attestation 신뢰 저하라는 세 갈래의 새로운 공격 표면을 만든다. 필자가 직접 구현한 `portfolio-passkey`의 실제 코드를 검토한 결과, 표준이 이미 제공하는 BE/BS 신호가 등록 시점에는 계산되고도 저장되지 않으며 로그인 시점에는 아예 재확인되지 않는다는 구체적인 사각지대를 확인했다.

### 6.2 한계점

본 연구는 단일 사례(`portfolio-passkey`) 분석에 기반하므로 일반화에는 한계가 있다. 또한 4.2절의 실측표는 제출 전 필자가 실제 기기로 검증해야 하는 항목으로 남아 있으며, attestation 관련 논의는 공개된 표준 문서와 각 사업자의 공식 설명에 의존했을 뿐 사업자 내부 구현을 직접 검증하지는 못했다.

### 6.3 향후 연구 방향

여러 서비스의 실제 프로덕션 로그를 대상으로 BE/BS 값의 시간에 따른 변화(0→1 전환)를 실측하는 정량 연구, 그리고 5.1절에서 제안한 위험 기반 재인증 장치를 실제로 구현해 그 효과를 검증하는 후속 연구를 향후 과제로 남긴다.
