# 동기화 패스키가 바꾼 FIDO2 위협모델과 RP의 사각지대
## — BE/BS 플래그 실측을 통한 사례 분석

**진혜정**
작성일: 2026년 9월 10일

---

## 초록

FIDO2/WebAuthn은 "개인키가 인증장치를 벗어나지 않는다"는 전제 위에서 피싱 저항성을 확보해 왔다. 그러나 애플·구글 등 플랫폼 사업자가 개인키를 클라우드 계정에 종단간 암호화로 동기화하는 **동기화 패스키(synced passkey)** 를 소비자 인증의 기본 경로로 채택하면서, 이 전제는 더 이상 모든 패스키에 보편적으로 성립하지 않는다. 미국 NIST는 2024년 SP 800-63B 보충 지침에서 "동기화는 AAL3의 비수출성(non-exportability) 요구사항을 위반한다"고 명시하면서도, 검증자(verifier)가 **Backup Eligibility(BE) 플래그를 근거로 동기화 인증장치를 제한하는 정책을 세울 수 있다**고 규정했다. 즉 표준은 이미 RP에게 판단 근거를 제공하고 있다.

본 연구는 새로운 프로토콜이나 게이트웨이를 제안하는 대신, **그 신호가 실제 RP 구현에서 어떻게 소비되는가**를 묻는다. 필자가 직접 설계·구현하여 공개 배포 중인 패스키 전용 인증 시스템을 대상으로, Chrome DevTools Protocol의 가상 authenticator를 이용해 BE/BS 플래그를 직접 제어하는 재현 가능한 실측을 수행하였다. 그 결과 세 가지를 확인하였다. 첫째, 서버가 사용하는 검증 라이브러리는 등록뿐 아니라 **모든 로그인 응답에서** BE/BS에 대응하는 값을 계산해 반환하고 있었다. 둘째, 해당 시스템은 그 값을 등록 시점에 HTTP 응답으로 전송하면서도 데이터베이스에 저장하지 않았고, 클라이언트 역시 그 값을 전혀 소비하지 않았다. 셋째, 등록 이후 자격증명의 백업 상태가 0에서 1로 전이하는 상황을 재현했을 때, 전송된 authenticatorData의 플래그 바이트는 `0x0d`에서 `0x1d`로 명확히 변화했음에도 **서버의 응답과 저장 상태는 완전히 동일**하였다. 즉 "기기 안에만 있던 자격증명이 어느 순간 클라우드 계정에도 존재하게 되었다"는 위협모델의 근본적 변화를 RP가 전혀 인지하지 못하는 사각지대가 실증되었다.

이는 단일 시스템의 결함이 아니라, 표준이 제공하는 신호가 실무 구현에서 소비되지 않을 때 발생하는 구조적 간극의 사례이다. 본 연구는 이 간극을 메우기 위한 RP 관점의 완화 방안을 제시하고, 그 적용 비용을 실제 스키마 수준에서 논의한다.

**키워드**: FIDO2, WebAuthn, 패스키, 동기화 패스키, Backup Eligibility, Backup State, 위협모델, 인증장치 확증수준(AAL)

## 1. 서론

### 1.1 연구 배경

비밀번호는 재사용, 피싱, 크리덴셜 스터핑에 구조적으로 취약하다는 점이 오랫동안 지적되어 왔다. 그 대안으로 FIDO 얼라이언스와 W3C가 공동 표준화한 FIDO2(WebAuthn + CTAP)가 주요 플랫폼에 채택되었고, 특히 2022년 이후 "패스키(passkey)"라는 이름으로 소비자 서비스에 빠르게 확산되었다.

이 확산은 더 이상 전망이 아니라 측정된 사실이다. Bhardwaj와 Sastry가 2026년 발표한 대규모 실측 연구[9]는 Tranco 상위 10만 개 도메인을 대상으로 크롤러 기반 조사를 수행하여 **9,397개 사이트에서 패스키 지원을 확인**하였고, 이를 "조사한 사이트의 11.3%"로 보고하였다. 지원율은 사이트 인기도와 뚜렷한 상관을 보여 상위 100개 사이트에서는 20%인 반면 5만~10만위 구간에서는 6.9%에 그쳤다. 또한 저자들은 이 결과가 "가장 큰 수작업 목록이 보고한 것보다 62배 많은 사이트"라고 기술하여, 기존의 수작업 집계(Passwordless Directory 기준 163개 도메인)가 실제 규모를 크게 과소평가하고 있었음을 보였다. 패스키는 이미 웹 인증의 주변부가 아닌 본류에 진입한 것이다.

### 1.2 문제 제기

FIDO2가 비밀번호 대비 확보한 피싱 저항성의 근거는 **개인키가 인증장치 밖으로 나가지 않는다**는 전제였다. 서버가 침해되어도, 통신이 도청되어도, 사용자가 피싱 사이트에 속아도 개인키 자체는 노출되지 않는다. 이 전제가 FIDO2 위협모델의 기초를 이룬다.

그런데 사용자가 기기를 잃어버리면 계정도 함께 잃는다는 문제 — 이른바 계정 복구 문제 — 를 해결하기 위해, 애플의 iCloud 키체인과 구글의 비밀번호 관리자는 **개인키 자체를 사업자의 클라우드에 종단간 암호화된 형태로 동기화**한다[6][7]. 편의성 측면에서 이는 명백한 개선이지만, 위협모델의 관점에서는 전제의 치환이다. "개인키는 기기를 벗어나지 않는다"가 "개인키는 클라우드 계정을 벗어나지 않는다"로 바뀌며, 신뢰 경계가 물리적 기기 하나에서 사용자의 플랫폼 계정 전체로 확장된다.

Büttner와 Gruschka는 이 변화를 접근 수준별로 분류하여 "동기화 패스키의 보안은 사실상 패스키 제공자에게 집중된다"고 결론지었다[5]. NIST는 2024년 SP 800-63B 보충 지침에서 이를 정책 언어로 확정하였다 — 동기화 인증장치는 조건부로 AAL2를 충족할 수 있으나, **"동기화는 AAL3의 비수출성 요구사항을 위반한다"**[2].

주목할 점은 표준이 이 구분을 RP에게 감추지 않았다는 것이다. WebAuthn은 authenticatorData의 플래그 바이트에 BE(Backup Eligibility)와 BS(Backup State) 두 비트를 두어, 자격증명이 동기화 가능한 종류인지 그리고 현재 실제로 백업된 상태인지를 **매 인증마다** RP에게 전달한다[1]. NIST 보충 지침 역시 "검증자는 이 플래그를 사용하여 동기화 인증장치의 사용을 제한하는 정책을 수립할 수 있다(MAY)"고 명시한다[2].

그렇다면 실제 RP 구현은 이 신호를 소비하고 있는가? 본 연구의 문제의식은 여기서 출발한다.

### 1.3 연구 질문과 기여

본 연구는 다음 세 가지 질문에 답한다.

- **RQ1.** 동기화 패스키의 도입은 기존 FIDO2 위협모델의 어떤 전제를 무너뜨리며, 그로 인해 어떤 공격 표면이 새로 생기는가?
- **RQ2.** 표준이 제공하는 BE/BS 신호는 실제 RP 구현에 어느 지점까지 도달하며, 어디서 소실되는가?
- **RQ3.** 그 소실이 만드는 사각지대는 구체적으로 무엇이며, 어떤 비용으로 메울 수 있는가?

이에 대한 본 연구의 기여는 다음과 같다.

1. **위협모델의 체계적 재검토**: 동기화 도입으로 발생한 공격 표면을 클라우드 계정 탈취, 복구·이관 경로, attestation 신뢰 저하, 폴백 다운그레이드, 자격증명 이식성의 다섯 축으로 정리하고, NIST AAL 체계와 연결하였다(3장).
2. **재현 가능한 실측**: Chrome DevTools Protocol의 가상 authenticator로 BE/BS를 직접 제어하여, 실제 배포 중인 시스템에서 신호가 소실되는 지점을 코드 수준까지 추적하였다. 측정 스크립트와 원본 결과를 함께 공개한다(4장, 부록 A·B).
3. **백업 상태 전이의 비가시성 실증**: 등록 이후 BS가 0에서 1로 전이할 때, 전송된 플래그 바이트는 변하지만 RP의 응답과 저장 상태는 완전히 동일함을 실측으로 보였다(4.4절). 이는 선행 연구가 이론적으로 지적해 온 문제를 실제 배포 시스템에서 확인한 것이다.
4. **적용 비용을 포함한 완화 방안**: 스키마 두 컬럼 추가와 검증 코드 수정만으로 전이 탐지가 가능함을 구체적으로 제시하고, 동시에 attestation 정책과 보조키 확장의 현실적 한계를 함께 논의하였다(5장).

### 1.4 논문의 구성

2장에서 FIDO2/WebAuthn의 구조와 BE/BS 플래그, 동기화 패스키의 구현 방식, 관련 연구를 정리한다. 3장에서 위협모델을 재검토하고 공격 표면을 분류한다. 4장에서 실제 배포 시스템을 대상으로 한 실측 결과를 제시한다. 5장에서 완화 방안과 그 한계를 논의하고, 6장에서 결론을 맺는다.

## 2. 배경 및 관련 연구

### 2.1 FIDO2/WebAuthn 인증 구조

WebAuthn의 등록(registration) 절차에서 인증장치는 RP별로 공개키·개인키 쌍을 생성하고, **공개키만** RP 서버에 전달한다. 인증(authentication) 절차에서는 서버가 발급한 일회용 challenge에 개인키로 서명하여 응답하며, 서버는 저장해 둔 공개키로 이를 검증한다.

이 구조가 제공하는 보안 속성은 두 가지 축으로 요약된다.

- **서버 침해 내성**: 서버가 보관하는 것은 공개키뿐이므로, 데이터베이스가 통째로 유출되어도 그것으로 로그인할 수 없다. 비밀번호 해시와 달리 오프라인 크래킹의 대상 자체가 존재하지 않는다.
- **피싱 저항성**: 서명 대상에 origin과 rpID가 포함되므로, 사용자가 피싱 사이트에 속더라도 그 사이트의 origin으로는 정상 서비스에 유효한 서명이 만들어지지 않는다.

두 속성 모두 "개인키가 인증장치 내부를 벗어나지 않는다"는 전제에 의존하지 않는다는 점에 유의할 필요가 있다. 서버 침해 내성과 피싱 저항성은 공개키 암호와 origin 바인딩에서 나오며, 동기화 여부와 무관하게 유지된다. 동기화가 바꾸는 것은 **개인키에 접근할 수 있는 경로의 수와 성격**이다. 이 구분은 3장의 논의 전반에서 중요하다.

### 2.2 authenticatorData와 플래그 바이트

모든 WebAuthn 응답에는 `authenticatorData`가 포함된다. 그 구조는 RP ID 해시 32바이트, 플래그 1바이트, 서명 카운터 4바이트, 그리고 선택적 필드들로 이어진다. 이 중 **33번째 바이트(0-based index 32)** 인 플래그 바이트가 본 연구의 핵심 대상이다.

WebAuthn Level 3 규격[1]이 정의하는 비트 배치는 다음과 같다.

| 비트 | 마스크 | 이름 | 의미 |
|---|---|---|---|
| 0 | 0x01 | UP (User Present) | 사용자가 물리적으로 조작했는가 |
| 1 | 0x02 | RFU1 | 예약 |
| 2 | 0x04 | UV (User Verified) | 생체인식·PIN 등으로 사용자를 확인했는가 |
| 3 | 0x08 | **BE (Backup Eligibility)** | 이 자격증명이 백업·동기화될 수 있는 종류인가 |
| 4 | 0x10 | **BS (Backup State)** | 이 자격증명이 현재 백업된 상태인가 |
| 5 | 0x20 | RFU2 | 예약 |
| 6 | 0x40 | AT | 첨부된 자격증명 데이터 포함 여부 |
| 7 | 0x80 | ED | 확장 데이터 포함 여부 |

이 비트 배치는 본 연구의 대상 시스템이 실제로 사용하는 검증 라이브러리 `@simplewebauthn/server` v13.3.3의 소스에서도 동일하게 확인된다(`esm/helpers/parseAuthenticatorData.js`, 18–23행)[8].

```js
const flags = {
    up: !!(flagsInt & (1 << 0)), // User Presence
    uv: !!(flagsInt & (1 << 2)), // User Verified
    be: !!(flagsInt & (1 << 3)), // Backup Eligibility
    bs: !!(flagsInt & (1 << 4)), // Backup State
    at: !!(flagsInt & (1 << 6)), // Attested Credential Data Present
    ed: !!(flagsInt & (1 << 7)), // Extension Data Present
};
```

### 2.3 BE와 BS의 의미론적 비대칭

두 플래그는 이름이 비슷하지만 시간적 성격이 근본적으로 다르며, 이 비대칭이 본 연구의 논지를 지탱한다.

**BE는 불변이다.** 규격은 백업 적격성을 "자격증명의 속성이며 주어진 공개키 자격증명 소스에 대해 영구적(permanent)"이라고 규정한다[1]. BE=1인 자격증명을 다중기기 자격증명(multi-device credential), BE=0인 것을 단일기기 자격증명(single-device credential)이라 부른다. 즉 BE는 등록 시점에 한 번 확인해 저장하면 충분하다.

**BS는 가변이다.** 규격은 BS를 "해당 자격증명을 사용한 임의의 ceremony에서 관찰된 최신 값"으로 정의하며, 백업 상태는 시간에 따라 변할 수 있다고 명시한다[1]. 예를 들어 사용자가 등록 당시에는 클라우드 동기화를 꺼 두었다가(BS=0) 나중에 켜면, 그 이후의 인증부터 BS=1이 실려 온다.

이 비대칭은 실무 지침에서도 강조된다. Yubico의 고보증 RP 구현 가이드는 "BS는 등록과 인증 사이에 변할 수 있으므로 지속적인 모니터링이 필요하다"고 명시한다[10]. 다시 말해, **BS는 등록 시점 1회 확인으로는 충분하지 않은 신호**다. 4장의 실측은 정확히 이 지점을 겨눈다.

라이브러리 수준에서도 두 플래그의 관계에 대한 불변식이 강제된다. `parseBackupFlags`는 BE=0이면서 BS=1인 조합, 즉 "백업될 수 없는 자격증명이 백업되었다"는 모순된 상태에 대해 `InvalidBackupFlags` 예외를 발생시킨다[8].

### 2.4 동기화 패스키의 구현 방식

**애플(iCloud 키체인).** 패스키는 종단간 암호화되어 동기화되며, 복구를 위해 HSM(하드웨어 보안 모듈) 클러스터에 에스크로된다. 복구 시 사용자는 Apple 계정 암호로 인증하고 등록된 전화번호로 온 SMS에 응답한 뒤 iCloud 보안 코드를 입력해야 하며, HSM 클러스터는 SRP 프로토콜로 보안 코드 지식을 검증한다(코드 자체는 애플에 전송되지 않는다). 무차별 대입을 막기 위해 **인증 시도는 10회로 제한**되고, 10번째 실패 시 HSM 클러스터는 에스크로 레코드를 파기한다[6].

**구글(비밀번호 관리자).** 패스키 개인키는 사용자 기기에서 하드웨어로 보호된 키로 암호화된 뒤 종단간 암호화 상태로만 업로드되며, 구글 자신이나 구글 내부의 공격자도 이를 사용할 수 없다. 화면 잠금(PIN·패턴·비밀번호)이 지식 요소로 요구되며, 새 기기에서 복구하려면 Google 비밀번호 관리자 PIN 또는 기존 기기의 화면 잠금을 알아야 한다[7].

두 구현 모두 암호학적으로는 견고하게 설계되어 있다. 그러나 **암호학적 견고함과 위협모델의 불변성은 다른 문제**다. 두 방식 모두 "사용자의 플랫폼 계정과 그 복구 절차가 안전하다"는 새로운 전제를 도입하며, 이 전제는 기존 FIDO2 위협모델에 존재하지 않았다.

### 2.5 관련 연구

**클라우드 저장소 침해 탐지.** Islam 등[3]은 USENIX Security 2025에서 CASPER를 제안하였다. 패스키 관리 서비스(PMS)의 클라우드 저장소가 침해되어 패스키가 유출되는 상황을 위협모델로 삼고, 실제 패스키를 구별 불가능한 미끼(decoy) 패스키들 사이에 숨겨 두어 유출된 패스키의 오용을 웹 서비스 제공자가 탐지할 수 있게 하는 최초의 프레임워크다. 본 연구와 문제의식을 공유하지만 접근이 상보적이다. CASPER는 **PMS와 RP 양쪽에 새로운 메커니즘을 도입**해야 하는 프레임워크이며 저자들 스스로 개념 증명 단계임을 밝히고 있다. 반면 본 연구는 **표준이 이미 제공하고 있으나 소비되지 않는 신호**에 주목하며, 새로운 메커니즘 없이 RP 측 구현만으로 개선 가능한 지점을 다룬다.

**동기화와 기기 바운드의 비교 평가.** Büttner와 Gruschka[5]는 ICISSP 2025에서 패스키 접근 수준을 유형화하여 동기화가 보안과 가용성에 미치는 영향을 분석하고, 동기화 패스키의 보안이 사실상 패스키 제공자에게 집중된다고 결론지었다. 본 연구는 이 분석에 **RP 구현 실태라는 경험적 층위**를 더한다.

**대인관계 위협모델.** Daffalla 등[4]은 USENIX Security 2025에서 친밀한 파트너 폭력 등 대인관계 위협 상황에서의 패스키를 분석하는 남용가능성(abusability) 분석 프레임워크를 제시하고, 패스키 지원 서비스 19개에 적용하여 다양한 남용 벡터를 식별하였다. 본 연구가 다루는 원격 공격자 모델과는 위협 주체가 다르지만, "기기를 공유하는 상황에서 동기화된 자격증명이 무엇을 의미하는가"라는 질문에서 접점을 갖는다.

**배포 실태 측정.** Bhardwaj와 Sastry[9]는 상위 10만 사이트를 대상으로 패스키 채택률을 측정하였다(1.1절). 다만 이 연구는 채택 여부와 구현 방식(자체 구현 대 외부 신원 제공자 위임)에 초점을 두었고, 채택한 사이트들이 BE/BS 신호를 어떻게 처리하는지는 다루지 않았다.

**RP 구현의 보안 분석.** Jannett 등[19]은 USENIX Security 2026에서 872개 패스키 지원 사이트를 분석하여, 그중 53개가 피싱·세션 고정 등 높은 CVSS 점수의 공격에 취약함을 보고하였다. 이들은 클라이언트(브라우저)와 인증장치 계층을 **모두 에뮬레이션**하는 보안 테스트 도구를 개발하여 RP 구현을 분석하였는데, 이는 본 연구가 4.2절에서 채택한 접근(가상 authenticator로 인증장치 계층을 제어하여 RP의 반응을 관찰)과 방법론적으로 같은 계열이다. 다만 공개된 초록과 아티팩트 문서만으로는 이 연구가 BE/BS 플래그 처리를 분석 대상에 포함했는지 확인할 수 없었다. 본 연구는 그 특정 질문을 단일 시스템에 대해 코드 수준까지 파고들어 답한다.

**본 연구의 위치.** 선행 연구들은 (a) 동기화가 위협모델을 바꾼다는 점을 이론적으로 규명하고[5], (b) 클라우드 침해를 탐지하는 새로운 메커니즘을 제안하며[3], (c) 채택률을 측정하고[9], (d) RP 구현의 취약점을 대규모로 조사하였다[19]. 본 연구는 이들 사이에 놓인 좁은 빈틈 — **표준이 이미 준 BE/BS 신호가 실제 RP 코드에서 어디까지 도달하고 어디서 버려지는가** — 를 하나의 시스템에 대한 깊은 추적으로 채운다.

## 3. 위협모델 재검토

### 3.1 기존 전제와 그 유효 범위

기존 FIDO2 위협모델은 다음을 방어선으로 삼았다.

> 공격자가 RP 서버, 통신 구간, 사용자의 비밀번호를 모두 확보하더라도 개인키는 얻을 수 없다.

BE=0인 하드웨어 바운드 자격증명에 대해서는 이 명제가 여전히 성립한다. 그러나 BE=1인 동기화 패스키에서는 개인키에 도달할 수 있는 경로가 하나 추가된다 — 사용자의 플랫폼 계정이다. 정확히 말하면 개인키는 여전히 평문으로 클라우드에 있지 않으나, **복호화 능력이 사용자 플랫폼 계정의 통제 하에 놓인다**.

### 3.2 신뢰 경계의 이동

| 구분 | 하드웨어 바운드 (BE=0) | 동기화 패스키 (BE=1) |
|---|---|---|
| 개인키 존재 범위 | 물리적 인증장치 1개 | 사용자 플랫폼 계정에 연결된 모든 기기 |
| 신뢰의 기초 | 인증장치의 물리적 보안 | 플랫폼 계정의 보안 + 그 복구 절차 |
| 기기 분실 시 | 해당 자격증명 폐기 후 재등록 필요 | 다른 기기에서 계속 사용 가능(가용성 이득) |
| 플랫폼 계정 탈취 시 | 영향 없음 | 동기화된 모든 서비스의 자격증명이 위험 |
| 침해의 파급 범위 | 서비스 1개 × 기기 1개 | 플랫폼 계정 1개 → 다수 서비스 |
| RP의 검증 수단 | attestation으로 비교적 신뢰 가능 | BE/BS 자기 보고 값에 의존 |
| NIST AAL[2] | AAL3까지 가능 | AAL2까지 (비수출성 요구 위반) |

핵심은 마지막에서 두 번째 행이다. 동기화 이전의 위협모델에서 침해의 파급 범위는 곱셈이 아니라 덧셈이었다. 기기 하나를 잃으면 그 기기의 자격증명만 위험했다. 동기화 이후에는 **플랫폼 계정 하나가 다수 서비스로 향하는 단일 실패 지점**이 된다.

### 3.3 공격 표면 A — 플랫폼 계정 탈취를 통한 간접 노출

공격자가 사용자의 애플·구글 계정을 장악하면, 그 계정에 동기화된 패스키에 접근할 조건이 갖춰진다. 서비스를 하나씩 공격할 필요 없이 계정 하나만 뚫으면 되는 구조다.

이 시나리오의 현실성을 뒷받침하는 전례로 2022년 LastPass 침해를 들 수 있다[11]. 공격자는 개발 환경 침해와 DevOps 엔지니어 개인 PC의 키로거 감염을 거쳐 백업 데이터베이스와 고객 비밀번호 볼트 사본을 유출하였다. 볼트는 암호화되어 있었으나, 이는 공격을 무산시킨 것이 아니라 **오프라인 크래킹의 시간 창을 열었을 뿐**이었다. 약한 마스터 비밀번호로 보호된 볼트는 시간을 들여 복호화되었고, 2025년 수사 기관은 1억 5천만 달러 규모의 암호화폐 절도를 이 침해와 연결지었으며 LastPass는 2,450만 달러 규모의 집단소송에 합의하였다[11].

이 전례가 동기화 패스키에 주는 함의는 다음과 같다. 클라우드 자격증명 저장소는 그 자체로 고가치 표적이며, 종단간 암호화는 침해 시점의 즉각적 피해를 막지만 **사용자 측 지식 요소(마스터 비밀번호, 화면 잠금 PIN, iCloud 보안 코드)의 강도가 최종 방어선**이 된다. 애플과 구글이 각각 HSM 시도 횟수 제한(10회)[6]과 기기 화면 잠금 요구[7]로 이 위험을 완화하고 있는 것은 정확히 이 때문이다. CASPER[3]가 상정한 위협모델도 동일한 지점을 겨눈다.

### 3.4 공격 표면 B — 복구 및 기기 이관 경로

패스키의 강점으로 흔히 "탈취할 비밀번호가 없다"는 점이 꼽히나, 이는 정상 로그인 경로에 한정된 서술이다. 기기 분실·교체 시 거치는 플랫폼 계정의 복구 절차는 여전히 전통적 인증 수단에 의존한다. 애플의 경우 계정 암호와 **등록된 전화번호로의 SMS**, 그리고 iCloud 보안 코드가 요구된다[6].

여기서 공격의 무게중심이 이동한다. 공격자는 패스키를 위조하거나 서명을 깨뜨릴 필요가 없다. **복구 절차를 통과해 새 기기를 계정에 인가시키면, 동기화된 패스키가 그 기기로 정상적으로 내려온다.** 최근의 실무 보고는 이를 두고 헬프데스크와 계정 복구가 공격자가 노리는 실질적 통제 지점이 되었으며, 같은 보호된 키체인을 새롭고 알려지지 않은 기기로 복제할 수 있게 된다고 지적한다[12].

이 경로의 특성은 **암호학적으로 완전히 정상인 인증으로 관측된다**는 점이다. RP 입장에서 그 로그인은 유효한 서명, 통과된 사용자 검증(UV), 정상적인 challenge 응답을 갖춘 흠결 없는 인증이다. 이것이 3.7절에서 논의할 탐지의 어려움으로 이어진다.

### 3.5 공격 표면 C — attestation 신뢰의 저하

WebAuthn은 등록 시 attestation을 통해 RP가 "이 자격증명이 어떤 종류의 인증장치에서 생성되었는가"를 암호학적으로 검증할 수 있는 수단을 제공한다. Yubico의 가이드는 attestation을 "RP가 사용할 수 있는 가장 강력한 신호"로 규정하며, 고보증 시나리오에서는 attestation 없는 자격증명을 거부하거나 제조사 화이트리스트를 운용할 것을 권한다[10].

그러나 소비자 대상 서비스에서 이 선택지는 사실상 닫혀 있다. 플랫폼 인증장치 대부분이 프라이버시를 이유로 익명화된 attestation을 제공하거나 아예 제공하지 않으며, 실무 해설은 "attestation이 없는 소비자 패스키는 항상 백업 적격(즉 동기화 패스키)으로 간주해야 한다"고 정리한다[13]. NIST 보충 지침 역시 연방 기관 내부 용도로는 attestation 활용을 권하면서도, **"attestation의 부재가 광범위한 대민 서비스에서 동기화 인증장치의 사용을 막아서는 안 된다(SHOULD NOT)"** 고 명시한다[2].

결과적으로 소비자 서비스의 RP는 attestation이라는 강한 신호를 실질적으로 쓸 수 없고, **인증장치가 스스로 보고하는 BE/BS 플래그가 사실상 유일한 판단 근거**가 된다. 이 신호는 암호학적으로 독립 검증되는 증거가 아니라 신뢰하는 플랫폼의 자기 보고라는 한계를 갖는다. 그럼에도 NIST가 이 플래그를 정책 수립 근거로 명시했다는 점[2]은, 완전하지 않더라도 이것이 현재 RP에게 주어진 최선의 수단임을 뜻한다. **그 최선의 수단조차 쓰이지 않고 있다면 문제는 신호의 품질이 아니라 소비의 부재다.**

4장은 이 가설을 실측으로 검증한다.

### 3.6 공격 표면 D — 폴백 다운그레이드

패스키의 피싱 저항성은 패스키가 실제로 사용될 때만 성립한다. Proofpoint 연구진이 2025년 8월 12일 공개한 다운그레이드 공격은 이 조건을 겨냥한다[14]. 모든 브라우저가 Microsoft Entra ID의 FIDO2 인증을 지원하지는 않는다는 점(예: 윈도우의 Safari)을 이용해, 피싱 프록시가 지원되지 않는 사용자 에이전트로 위장하면 패스키가 비활성화되고 사용자는 더 약한 수단으로 인증하도록 유도된다. 연구진은 이 기법이 특정 구현에 국한되지 않는다고 밝혔다. 이 방식은 암호를 깨지 않고 **인증 수단 선택 자체를 조작**한다[12].

이 공격 표면은 동기화 여부와 직접 관련되지는 않으나, 위협모델 재검토에서 함께 다뤄야 할 이유가 있다. 동기화 패스키가 "패스키만으로 충분하다"는 인식을 확산시키는 동안, 실제 계정의 보안 수준은 **가장 약한 폴백 경로**에 의해 결정되기 때문이다.

### 3.7 공격 표면 E — 자격증명 이식성의 제도화

FIDO 얼라이언스는 패스키를 제공자 간에 안전하게 옮기기 위한 Credential Exchange Format(CXF)과 Credential Exchange Protocol(CXP)을 표준화하고 있다. CXF v1.0은 2025년 3월 13일자 검토 초안(Review Draft)으로 공개되어 FIDO 제안 표준(Proposed Standard)이 되는 것을 목표로 하며, 자격증명을 제공자 간에 이전하거나 참조할 때의 상호운용성과 자원 소유자의 통제권을 확보하기 위한 데이터 구조를 규정한다. 이 작업은 FIDO 얼라이언스 Credential Provider SIG에서 1Password, 애플, Bitwarden, Dashlane, Enpass, 구글, 마이크로소프트, NordPass, Okta, 삼성, SK텔레콤 등이 함께 참여해 진행 중이다[15].

주목할 점은 참여 명단 그 자체다. 자격증명 저장을 담당하는 주요 사업자 전부가 **개인키를 제공자 간에 옮기는 표준**을 함께 만들고 있다.

이는 사용자 선택권 측면에서 바람직한 발전이지만, 위협모델 관점에서는 새로운 사실을 확정한다. **개인키의 이동은 이제 예외적 사건이 아니라 표준화된 정상 동작이다.** "개인키는 인증장치를 벗어나지 않는다"는 문장은 이제 특정 유형(BE=0)의 자격증명에만 적용되는 조건부 명제로 축소되었으며, RP가 그 유형을 구분하지 못한다면 자신이 어떤 보안 속성 위에서 동작하는지조차 알 수 없게 된다.

### 3.8 공격 표면 종합

| 표면 | 공격자가 필요로 하는 것 | RP에게 관측되는 모습 | RP가 쓸 수 있는 신호 |
|---|---|---|---|
| A. 플랫폼 계정 탈취 | 플랫폼 계정 자격증명 + 지식 요소 | 정상적인 유효 서명 | BE(위험 노출 여부), BS(백업 상태) |
| B. 복구·이관 악용 | 복구 절차 통과(SMS·계정 암호 등) | 정상적인 유효 서명 | BS 전이, 서명 카운터, 기기 문맥 |
| C. attestation 부재 | (공격이 아닌 구조적 제약) | 자격증명 유형 불명 | BE/BS 자기 보고값만 |
| D. 폴백 다운그레이드 | AiTM 프록시 + 브라우저 위장 | 패스키가 아예 쓰이지 않음 | 폴백 사용 여부 자체 |
| E. 자격증명 이식 | 제공자 간 이전 절차 | 정상적인 유효 서명 | BE, (제한적으로) BS |

표에서 드러나는 공통점이 있다. **A·B·E 모두 RP에게는 "정상적인 유효 서명"으로 관측된다.** 서명 검증만으로는 이들을 구분할 수 없으며, 구분의 실마리는 authenticatorData가 함께 실어 보내는 부가 신호 — 그중에서도 BE/BS — 에 있다.

### 3.9 NIST AAL 체계와의 접속

NIST SP 800-63B 보충 지침[2]은 동기화 인증장치에 대해 다음을 규정한다.

- 동기화 패브릭으로 내보내지는 인증키는 SP 800-131A가 정한 최소 보안 강도(112비트) 이상의 키로 **암호화된 형태로만 저장되어야 한다(SHALL)**. 이 암호화는 사용자 통제 비밀을 사용하는 것이 **바람직하다(SHOULD)**.
- 동기화 패브릭에 저장된 인증키는 **인증된 사용자만 접근 가능하도록 접근 통제로 보호되어야 한다(SHALL)**.
- 동기화 패브릭의 인증키에 대한 사용자 접근은 **AAL2 상당의 다중요소 인증으로 보호되어야 한다(SHALL)**.
- 모든 인증 트랜잭션의 개인키 연산은 **로컬 기기에서 수행되어야 한다(SHALL)**.
- **"AAL2 수준의 인증은 위 요구사항을 충족하는 조건에서 지원될 수 있다. 그러나 동기화는 AAL3의 비수출성 요구사항을 위반한다."**

마지막 문장이 3장 전체의 요약이다. 동기화 패스키는 "약한 인증 수단"이 아니라 **다른 확증 수준에 속하는 인증 수단**이며, 둘을 구분하지 못하는 RP는 자신의 계정 보안이 어느 수준에 있는지 알 수 없다. 그리고 같은 문서가 그 구분의 도구로 BE 플래그를 명시했다는 사실[2]은, 4장에서 확인할 실태와 대비될 때 문제의 성격을 분명히 한다.

## 4. 실측: 신호는 어디서 사라지는가

### 4.1 대상 시스템

측정 대상은 필자가 8번 과제로 직접 설계·구현하여 공개 배포 중인 패스키 전용 인증 시스템이다.

| 항목 | 내용 |
|---|---|
| 공개 주소 | `https://aleph-passkey.vercel.app` |
| 인증 방식 | 패스키 전용 — 이메일·비밀번호 없음 |
| 서버 | Vercel 서버리스 함수 (Node.js) |
| 검증 라이브러리 | `@simplewebauthn/server` v13.3.3 |
| 저장소 | Neon(PostgreSQL) |
| 자격증명 정책 | `residentKey: "required"`, `userVerification: "required"`, `attestationType: "none"` |

이 시스템을 대상으로 삼은 이유는 두 가지다. 첫째, 소스 코드 전체와 데이터베이스 스키마에 접근할 수 있어 **신호가 소실되는 지점을 코드 수준까지 추적**할 수 있다. 둘째, 이 시스템은 표준 라이브러리를 정석대로 사용하는 평범한 구현이며, 특별히 부주의하게 작성된 반례가 아니다 — 오히려 사용자 검증을 서버에서 재확인하고(`requireUserVerification: true`), 재인증 없이는 자격증명 삭제를 허용하지 않는 등 일반적인 튜토리얼 수준을 넘어서는 방어를 갖추고 있다. 그러한 구현에서도 BE/BS 신호가 소실된다면, 그 소실은 개별적 부주의가 아니라 구조적 간극일 가능성이 높다.

한 가지 짚어 둘 점은 `attestationType: "none"`(`api/register/options.js` 69행)이라는 선택이다. 3.5절에서 논의했듯 이는 소비자 서비스의 일반적 선택이며, 그 결과 이 RP는 자격증명 유형에 대해 **BE/BS 외의 판단 근거를 갖지 않는다**.

### 4.2 측정 방법

BE/BS는 인증장치가 결정하는 값이므로, 서로 다른 값을 관측하려면 성질이 다른 인증장치가 필요하다. 실제 하드웨어를 사용할 경우 재현성과 접근성 모두 문제가 된다. 본 연구는 **Chrome DevTools Protocol(CDP)의 가상 authenticator**를 사용하였다. CDP의 `WebAuthn.addVirtualAuthenticator`는 `defaultBackupEligibility`(BE)와 `defaultBackupState`(BS)를 옵션으로 받으며, `WebAuthn.setCredentialProperties`로 **생성 이후에 백업 상태를 변경**할 수도 있다[16].

이 도구 선택에는 방법론적 이점이 있다. 실제 기기로는 재현하기 어려운 "등록 이후 동기화가 켜지는" 전이를 정확한 시점에 유발할 수 있고, 제3자가 동일한 스크립트로 결과를 재현할 수 있다. 반면 한계도 분명하다 — 가상 authenticator는 플래그를 *신고*하는 소프트웨어일 뿐 실제 클라우드 동기화를 수행하지 않는다. 다만 본 연구의 관심사는 클라우드 동기화 자체가 아니라 **RP가 그 신호를 어떻게 처리하는가**이므로, 신호의 발생원이 가상이라는 점은 결론에 영향을 주지 않는다.

측정 스크립트는 세 가지 시나리오를 수행한다.

1. **동기화 패스키** — BE=1, BS=1로 설정한 인증장치로 신규 계정 등록 후 로그인
2. **하드웨어 바운드 패스키** — BE=0, BS=0으로 설정한 인증장치로 동일 절차
3. **등록 후 동기화 활성화** — BE=1, BS=0으로 등록 후 로그인 → `setCredentialProperties`로 BS를 1로 전환 → 다시 로그인

각 단계에서 (a) 브라우저가 실제로 전송한 `authenticatorData`의 플래그 바이트를 클라이언트 측에서 직접 디코딩하고, (b) 서버가 반환한 응답 본문을 기록하며, (c) 서버가 해당 자격증명에 대해 보관 중인 상태 전체를 조회하였다. 스크립트 전문과 원본 결과는 부록 A·B에 있다.

### 4.3 실측 1·2: 유형 구분은 정상 작동한다

| | 실측 1 (동기화) | 실측 2 (하드웨어 바운드) |
|---|---|---|
| 가상기기 설정 | BE=1, BS=1 | BE=0, BS=0 |
| 전송된 플래그 바이트 | `0x1d` (`00011101`) | `0x05` (`00000101`) |
| 해석 | UP=1, UV=1, BE=1, BS=1 | UP=1, UV=1, BE=0, BS=0 |
| 등록 응답 `credentialDeviceType` | `"multiDevice"` | `"singleDevice"` |
| 등록 응답 `backedUp` | `true` | `false` |
| 로그인 응답 | `{"ok":true,"deviceName":"…"}` | `{"ok":true,"deviceName":"…"}` |

두 유형은 플래그 바이트 수준에서 명확히 구분되며, 서버의 검증 라이브러리도 이를 정확히 해석한다. 즉 **신호는 서버까지 온전히 도달한다.** 등록 시점에 한해서는 RP가 동기화 여부를 알 수 있는 상태다.

그러나 로그인 응답은 두 경우 모두 동일하다. 이 시점에서 이미 다음 절의 결과가 예고된다.

### 4.4 실측 3: 백업 상태 전이는 관측되지 않는다

핵심 실험이다. BE=1, BS=0으로 등록한 자격증명 — 즉 "동기화될 수 있으나 아직 동기화되지 않은" 상태 — 의 백업 상태를 등록 이후에 1로 전환하였다. 이는 사용자가 패스키를 만든 뒤 클라우드 동기화를 뒤늦게 활성화한 상황에 대응한다.

| 단계 | 전송된 플래그 | 서버 응답 |
|---|---|---|
| 등록 | (BE=1, BS=0) | `credentialDeviceType: "multiDevice"`, `backedUp: false` |
| 전환 전 로그인 | `0x0d` → BE=1, **BS=0** | `{"ok":true,"deviceName":"[측정] 나중에 동기화 켜짐"}` |
| **BS 0→1 전환** | (성공) | — |
| 전환 후 로그인 | `0x1d` → BE=1, **BS=1** | `{"ok":true,"deviceName":"[측정] 나중에 동기화 켜짐"}` |

전송된 플래그 바이트는 `0x0d`에서 `0x1d`로 변화했다. 비트 4(BS)가 0에서 1로 바뀐 것이며, 이는 위협모델의 관점에서 **"이 자격증명이 방금 클라우드 계정에도 존재하게 되었다"**는, 3장에서 논의한 모든 공격 표면의 전제 조건이 성립했음을 뜻하는 사건이다.

그럼에도 서버의 응답 본문은 두 로그인에서 **문자 단위로 동일**했다.

전환 이후 서버가 해당 자격증명에 대해 보관 중인 상태 전체를 조회한 결과는 다음과 같다.

```json
{
  "id": "9C49xgSLKjgL23cF6ZQBaj84uyT4eTzCxAuXSkWC0Qk",
  "isCurrentSession": true,
  "shortId": "9C49xgSLKjgL",
  "deviceName": "[측정] 나중에 동기화 켜짐",
  "createdAt": "2026-09-10T03:51:52.969Z",
  "publicKey": "pAEBAycgBiFYILh3ylxjFsOTSkoEiQty1p6iz9HfXehTDg63ppK1IDz8",
  "signCount": 3
}
```

`signCount: 3`은 이 자격증명으로 등록 1회와 로그인 2회, 총 세 번의 ceremony가 수행되었음을 보여준다. 서버는 그 횟수를 세고 있었다. 그러나 그 세 번 사이에 자격증명이 단일기기 상태에서 클라우드 백업 상태로 전이했다는 사실은 **어디에도 남아 있지 않다.** 저장된 레코드에는 BE, BS, `credentialDeviceType`, `backedUp` 중 어느 것에 대응하는 필드도 존재하지 않는다.

### 4.5 코드 수준 원인 분석

신호가 소실되는 지점을 소스에서 추적한 결과, 세 개의 독립적인 지점이 확인되었다.

**(1) 등록 시점 — 계산되지만 저장되지 않는다.**
`api/register/verify.js` 63행은 검증 결과에서 두 값을 정확히 꺼내며, 95–103행은 이를 HTTP 응답에 담아 전송한다.

```js
const { credential, credentialDeviceType, credentialBackedUp } = verification.registrationInfo;
```

그러나 같은 파일 64–71행에서 데이터베이스에 저장할 레코드를 구성할 때 이 두 값은 포함되지 않는다. `db/schema.sql`의 `pk_credentials` 테이블 정의(20–28행)에도 대응 컬럼이 없다. 값은 응답으로 흘러 나가고 저장은 되지 않는다.

**(2) 클라이언트 — 전송되지만 소비되지 않는다.**
등록 응답에 실린 `credentialDeviceType`과 `backedUp`이 화면에서 어떻게 쓰이는지 확인하기 위해 클라이언트 코드 `app.js` 전체(25,670바이트)를 검색한 결과, `credentialDeviceType`, `backedUp`, `multiDevice` 중 어느 문자열도 **단 한 번도 등장하지 않았다.** 서버는 계산하여 보냈고, 클라이언트는 받아서 버린다. 사용자에게 "이 패스키는 다른 기기와 동기화됩니다"라고 알려 주는 표시조차 없다.

**(3) 로그인 시점 — 조회조차 되지 않는다.**
가장 중요한 지점이다. `api/login/verify.js` 79–83행은 검증 결과에서 서명 카운터만 꺼내 쓴다.

```js
const session = await store.bumpCounterAndCreateSession({
    credentialId: stored.id,
    counter: verification.authenticationInfo.newCounter,
    userId: stored.user_id,
});
```

그런데 라이브러리가 반환하는 `authenticationInfo`에는 `newCounter` 외에 `credentialDeviceType`과 `credentialBackedUp`이 함께 들어 있다. `@simplewebauthn/server` v13.3.3의 `verifyAuthenticationResponse.js` 152행이 매 인증마다 `parseBackupFlags(flags)`를 호출하고, 163–164행에서 그 결과를 반환 객체에 담는다[8]. 타입 정의(`verifyAuthenticationResponse.d.ts` 60–61행)도 이를 명시한다.

즉 **RP는 매 로그인마다 최신 BS 값을 손에 쥐고도 그것을 열어 보지 않는다.** 4.4절의 결과는 이 세 줄의 코드가 만든 것이다.

### 4.6 관찰의 일반화 가능성

단일 시스템에 대한 관찰이므로 일반화에는 신중해야 한다. 다만 다음 세 가지 정황은 이 소실이 개별 구현의 부주의가 아닐 가능성을 시사한다.

첫째, 소실은 **기본값을 따른 결과**이지 의도적 제거가 아니다. 세 지점 모두 "추가로 무언가를 하지 않았다"의 형태이며, 라이브러리가 반환하는 객체에서 필요한 필드만 구조 분해하는 것은 표준적인 코딩 관행이다. BE/BS를 쓰려면 개발자가 그 존재와 의미를 알고 **의식적으로 추가 코드를 작성해야 한다.**

둘째, 대상 시스템은 보안 측면에서 소홀한 구현이 아니다(4.1절). 그럼에도 이 신호는 누락되었다.

셋째, 표준과 실무 지침의 권고가 존재함에도[2][10] 그것이 라이브러리의 기본 동작이나 문서의 전면에 배치되어 있지 않다. BE/BS를 쓰지 않아도 인증은 완전히 정상 작동하므로, 개발자가 그 부재를 알아챌 계기 자체가 없다.

다만 이 세 정황이 "다른 RP도 그러하다"를 입증하지는 않는다. Jannett 등[19]은 872개 패스키 지원 사이트의 RP 구현을 대규모로 분석하였으므로 RP 실태 조사 자체가 공백인 것은 아니며, 본 연구가 확인하지 못한 것은 그 조사가 BE/BS 처리를 다루었는지 여부다(2.5절). 따라서 본 절의 논의는 정황 근거이지 통계적 일반화가 아니며, 실제 분포의 확인은 6.3절에서 향후 과제로 남긴다.

정리하면, 본 연구의 결과는 "모든 RP가 그렇다"는 주장이 아니라 **"표준을 정석대로 따르고 다른 방어는 충실히 갖춘 구현에서도 이 신호는 기본적으로 소실된다"는 존재 증명**으로 제시된다.

### 4.7 보조 관찰: 실제 기기에서의 동기화 확인

가상 authenticator를 사용한 위 실측과 별도로, 본 시스템 구축 과정에서 실제 기기를 통한 관찰이 기록되어 있다. 2026년 9월 3일 아이폰의 Face ID로 패스키를 등록한 결과 해당 자격증명은 iCloud 키체인에 저장되었으며, **같은 계정에 두 번째 패스키를 추가하려 하자 "이미 등록되어 있다"는 이유로 거절**되었다. 이는 `excludeCredentials`가 정상 작동한 결과인 동시에, iCloud 키체인이 동일 패스키를 기기 간에 동기화하기 때문에 별개의 기기가 동일한 자격증명을 제시했음을 보여준다.

이 관찰은 2.4절에서 서술한 동기화 동작이 실제 환경에서 재현됨을 확인해 주며, 4.3–4.4절의 가상 authenticator 실측이 현실의 동작을 왜곡 없이 모사하고 있음을 뒷받침한다.

## 5. 완화 방안과 그 한계

### 5.1 BE/BS의 지속 기록과 전이 탐지

4장에서 확인한 사각지대는 원리적으로 어렵지 않게 메울 수 있다. 필요한 것은 두 가지다.

**(a) 등록 시점의 값을 저장한다.** 자격증명 테이블에 두 컬럼을 추가한다.

```sql
alter table pk_credentials add column if not exists backup_eligible boolean;
alter table pk_credentials add column if not exists backed_up boolean;
```

**(b) 매 인증마다 최신 값을 확인하고 갱신한다.** 로그인 검증 시 이미 손에 들어와 있는 값을 함께 꺼내어, 저장된 값과 비교한 뒤 갱신한다.

```js
const { newCounter, credentialBackedUp } = verification.authenticationInfo;
// stored.backed_up === false && credentialBackedUp === true
//   → 이 자격증명이 방금 클라우드 백업 범위에 들어왔다
```

BE는 불변이므로 등록 시 한 번 저장하면 충분하고, BS만 매번 갱신하면 된다(2.3절). 이 변경은 스키마 두 컬럼과 검증 코드 수 행에 불과하며, 추가적인 왕복이나 사용자 상호작용을 요구하지 않는다. **4.4절에서 실증한 사각지대는 이 정도의 비용으로 닫힌다.**

여기서 얻어지는 것은 단순한 기록이 아니다. BS의 0→1 전이는 "이 계정의 자격증명이 방금 다른 신뢰 경계로 확장되었다"는 의미를 갖는 **보안 이벤트**이며, 이를 포착하면 다음 절의 정책이 가능해진다.

### 5.2 위험 기반 재인증

전이를 탐지할 수 있게 되면, 그것을 정책에 연결할 수 있다.

- **BS 0→1 전이 직후**: 되돌릴 수 없는 동작(자격증명 삭제, 민감 자료 열람, 계정 설정 변경) 앞에 재인증을 요구한다. 대상 시스템은 이미 `pk_sessions.reauth_at` 기반의 재확인 장치를 갖추고 있으므로(자격증명 삭제 시 5분 이내의 재확인을 요구), 그 트리거 조건에 BS 전이를 추가하는 형태로 확장할 수 있다.
- **BE=1 자격증명의 최초 등록 시**: 사용자에게 그 의미 — 이 패스키는 플랫폼 계정을 통해 다른 기기에서도 사용될 수 있다 — 를 명시적으로 고지한다. 4.5절에서 확인했듯 현재는 서버가 그 사실을 알고 있으면서도 화면에 표시하지 않는다.
- **사후 감사**: 침해가 의심될 때 "이 계정의 자격증명이 언제 클라우드 범위로 들어갔는가"를 답할 수 있게 된다. 현재 구조에서는 이 질문에 답할 근거 자체가 존재하지 않는다.

다만 한계도 분명하다. BS 전이 탐지는 **공격을 차단하지 못하며, 위험 노출의 변화를 인지하게 할 뿐이다.** 3.4절에서 논의한 복구 경로 악용의 경우, 공격자가 정상적으로 복구를 통과했다면 그 로그인은 흠결 없는 인증으로 관측된다. BS는 "이 자격증명이 다른 기기로 갈 수 있는 상태"임을 알려 줄 뿐, "지금 서명한 것이 정당한 사용자인가"에는 답하지 못한다.

### 5.3 attestation 정책과 그 현실적 제약

이론적으로 가장 강력한 대응은 등록 시 attestation을 요구하여 BE=0인 자격증명만 허용하는 것이다[10]. 금융이나 관리자 계정처럼 보안 민감도가 높은 맥락에서는 타당한 선택이며, NIST의 AAL3 요구사항과도 정합한다[2].

그러나 3.5절에서 논의했듯 소비자 대상 서비스에서는 두 가지 제약이 있다. 첫째, 플랫폼 인증장치 대부분이 유의미한 attestation을 제공하지 않으므로 이 정책은 사실상 "플랫폼 패스키 전면 거부"가 되어 가용성을 심각하게 훼손한다. 둘째, NIST 자신이 대민 서비스에서 attestation 부재를 이유로 동기화 인증장치를 막지 말 것을 권고한다[2].

따라서 현실적인 설계는 **일률적 거부가 아니라 차등화**다. 일상적 열람은 동기화 패스키로 허용하되, 되돌릴 수 없는 동작에 대해서만 더 높은 확증을 요구하는 방식이다.

### 5.4 기기 바운드 보조키 — 기대와 현실

동기화 자격증명에 기기 고유 키를 덧붙여 RP가 물리적 기기를 식별할 수 있게 하는 접근이 표준화 과정에서 논의되었다. `devicePubKey` 확장이 그것으로, 다중기기 자격증명에 자동 생성된 기기 바운드 키 쌍을 짝지어 로그인 시 위험 분석에 기기 정보를 반영할 수 있게 하려는 시도였다.

그러나 이 방향은 현재 의존할 수 있는 대안이 아니다. `devicePubKey`는 더 넓은 범위를 다루는 `supplementalPubKeys`로 대체되었으나, 그 `supplementalPubKeys`마저 규격에서 제거되었다. Adam Langley가 2024년 8월 1일 제출한 Pull Request #2109 "Drop the supplementalPubKeys extension"이 같은 달 7일 워킹그룹 회의를 거쳐 병합되었으며, 제거 사유는 이 확장이 **"Level 3 기간 내에 상호운용 가능한 두 개의 구현"이라는 요건을 충족하지 못할 것**이라는 판단이었다[17].

이는 단순한 구현 지연이 아니라 표준화 실패다. "동기화의 편의를 유지하면서 기기 식별을 회복한다"는 기술적 해법은 수년에 걸친 표준화 시도 끝에 채택되지 못했고, 그 자리는 현재 비어 있다.

이 사실은 5.1절 제안의 상대적 가치를 높인다. 정교한 확장 기능을 기다릴 수 없는 상황에서, **이미 모든 응답에 실려 오는 BE/BS를 읽는 것이 지금 당장 가능한 유일한 대응**이기 때문이다.

### 5.5 폴백 경로의 관리

3.6절의 다운그레이드 공격에 대한 대응은 패스키 자체가 아니라 그 주변에 있다. 계정에 남아 있는 약한 인증 수단(SMS OTP, 이메일 매직링크, 지식 기반 질문)은 패스키의 피싱 저항성을 우회하는 경로가 된다. 실무적 권고는 가능한 한 레거시 인증 수단을 비활성화하고, 브라우저 미지원을 이유로 한 자동 폴백을 제한하는 것이다[14].

본 연구의 대상 시스템은 이 점에서 특이한 위치에 있다. 이메일도 비밀번호도 없고 폴백 경로가 아예 존재하지 않으므로 다운그레이드 공격 표면이 원천적으로 없다. 다만 그 대가로 **마지막 패스키를 잃으면 계정을 복구할 방법이 없으며**, 시스템은 이를 막는 대신 화면에 경고하는 방식을 택하고 있다. 이는 3.4절에서 논의한 "복구 절차가 곧 공격 표면"이라는 딜레마의 다른 쪽 끝을 보여주는 설계 선택이다.

### 5.6 표준 및 생태계 동향

WebAuthn Level 3은 RP가 클라이언트에 자격증명 상태를 통지하는 Signal API(`signalUnknownCredential`, `signalAllAcceptedCredentials`, `signalCurrentUserDetails`)를 도입하였다[13]. 이는 RP가 삭제한 자격증명이 사용자 기기의 패스키 목록에 남아 혼란을 주는 문제를 완화한다. 다만 이 API는 "fire-and-forget" 방식으로 반환값이 없어 RP가 결과를 확인할 수 없으며, 본 연구가 다루는 상태 관측 문제를 직접 해결하지는 않는다.

CXF/CXP의 표준화(3.7절)는 반대 방향의 압력으로 작용한다. 자격증명 이동이 표준화된 정상 동작이 될수록, RP가 "지금 이 자격증명이 어떤 신뢰 경계 위에 있는가"를 스스로 추적할 필요는 커진다.

### 5.7 제안의 요약

| 대응 | 효과 | 비용 | 현재 실행 가능성 |
|---|---|---|---|
| BE/BS 저장·전이 탐지 (5.1) | 위험 노출 변화 인지, 사후 감사 가능 | 컬럼 2개 + 코드 수 행 | **즉시 가능** |

## 6. 결론

### 6.1 요약

동기화 패스키의 확산은 FIDO2가 전제했던 "개인키는 인증장치를 벗어나지 않는다"를 "개인키는 플랫폼 계정을 벗어나지 않는다"로 치환하였다. 이는 신뢰 경계를 기기에서 계정으로 확장시키며, 플랫폼 계정 탈취·복구 경로 악용·attestation 신뢰 저하·폴백 다운그레이드·자격증명 이식성이라는 다섯 갈래의 공격 표면을 만든다(3장). NIST는 이 변화를 확증 수준의 문제로 규정하여 동기화 인증장치가 AAL3의 비수출성 요구를 위반한다고 명시하는 한편, BE 플래그를 RP의 정책 수단으로 제시하였다[2].

그러나 실제 배포 중인 시스템을 대상으로 한 실측 결과, 그 신호는 RP 구현에 도달하고도 소비되지 않았다. 검증 라이브러리는 등록과 **모든 인증**에서 BE/BS를 계산해 반환하지만, 대상 시스템은 그 값을 저장하지 않았고(등록), 화면에 표시하지 않았으며(클라이언트), 조회조차 하지 않았다(로그인). 그 결과 자격증명의 백업 상태가 0에서 1로 전이하여 전송 플래그가 `0x0d`에서 `0x1d`로 변화한 상황에서도, **서버의 응답과 저장 상태는 완전히 동일**하였다(4.4절). 위협모델이 근본적으로 바뀌는 사건이 RP에게는 아무 일도 아닌 것으로 관측된 것이다.

이 사각지대는 스키마 두 컬럼과 검증 코드 수 행으로 닫을 수 있다(5.1절). 반면 기술적으로 더 정교한 대안인 기기 바운드 보조키는 표준화 과정에서 방향이 바뀌고 주요 플랫폼의 지원이 중단되어 현재 의존할 수 없다(5.4절). 즉 **지금 RP가 할 수 있는 가장 실효적인 일은, 이미 매 응답에 실려 오는 신호를 읽는 것이다.**

### 6.2 한계

본 연구는 다음의 한계를 갖는다.

- **단일 사례 기반**: 하나의 시스템에 대한 심층 분석이므로 통계적 일반화가 불가능하다. 4.6절에서 논의한 정황 근거는 가능성을 시사할 뿐 증명은 아니다.
- **가상 authenticator의 사용**: 실측은 CDP 가상 authenticator로 수행되었으며, 실제 클라우드 동기화가 일어난 것이 아니라 플래그가 그렇게 신고된 것이다. RP 측 처리를 관찰한다는 본 연구의 목적에는 부합하나, 플랫폼 제공자 측 동작을 검증한 것은 아니다.
- **플랫폼 내부 구현의 미검증**: 애플·구글의 동기화 및 에스크로 구조에 대한 서술은 각사가 공개한 문서에 의존하였으며[6][7], 내부 구현을 독립적으로 검증하지 못하였다.
- **공격의 실증 부재**: 3장에서 정리한 공격 표면 중 실제로 실행해 본 것은 없다. 본 연구가 실증한 것은 공격의 성공이 아니라 **관측 능력의 부재**다.

### 6.3 향후 연구

- **BE/BS 처리 실태의 대규모 조사**: 본 연구가 남긴 가장 직접적인 질문은 "다른 RP들은 이 신호를 쓰는가"이다. Jannett 등[19]이 개발한 클라이언트·인증장치 에뮬레이션 도구는 이 조사에 그대로 쓸 수 있는 기반이며, 본 연구의 실측 스크립트(부록 A)가 사용한 BS 전이 유발 기법을 결합하면 능동적 측정이 가능하다. 구체적으로는 (a) 등록 응답에서 자격증명 유형이 사용자에게 고지되는지, (b) BE=0만 허용하는 정책이 적용되는지, (c) BS를 0에서 1로 전이시킨 뒤 RP의 동작이나 사용자 알림에 변화가 있는지를 지표로 삼을 수 있다.
- **전이 탐지의 실효성 평가**: 5.1–5.2절의 제안을 실제 서비스에 적용하여, BS 전이가 얼마나 자주 관측되는지, 그것이 유의미한 위험 신호로 기능하는지를 정량적으로 평가할 필요가 있다.
- **CASPER와의 결합**: Islam 등[3]의 미끼 기반 탐지와 본 연구의 신호 기반 관측은 서로 다른 층위에서 동작하므로, 결합했을 때의 탐지율 변화를 살펴볼 여지가 있다.

측정 스크립트는 `10/측정-BE-BS.mjs`이며, 8번 과제의 검사 하네스(`8/portfolio-passkey/tools/harness.mjs`)를 재사용한다. 실행 방법은 다음과 같다.

```bash
node 10/측정-BE-BS.mjs https://aleph-passkey.vercel.app
```

스크립트는 헤드리스 크롬을 띄우고 CDP로 접속한 뒤, 시나리오마다 쿠키를 지우고 지정한 BE/BS 값을 갖는 가상 authenticator를 새로 부착한다. 각 시나리오에서 신규 계정을 등록하고 로그인하며, 브라우저가 전송한 `authenticatorData`의 33번째 바이트를 클라이언트 측에서 직접 디코딩하여 플래그를 추출한다. 원본 결과는 `10/측정결과-BE-BS.json`에 저장된다.

**측정 환경**: 대상 `https://aleph-passkey.vercel.app`, 측정 시각 2026-09-10T03:52:38Z, `@simplewebauthn/server` v13.3.3, 헤드리스 Chrome.
