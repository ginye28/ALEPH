분위기를 살리는 친화력

과제 1 · 9

"대화를 나누면 어느새 여러 사람이 웃고 있다"는 동료들의 반복된 말입니다.

일하는 방식

  • "막았다"는 상태 코드가 아니라 전후 데이터로 판정합니다. RLS 거절이 200 + 빈 배열로 오고, 스키마 오류가 거절처럼 보이는 경우를 둘 다 겪은 뒤 정한 원칙입니다 (과제 7).
  • 실사용에서 나온 제보를 회귀 검사로 바꿉니다. 순차 검사가 잡지 못한 삭제 경합을 연타 재현 검사로 남겼습니다 (과제 8).
  • 결과에 가설을 맞추지 않습니다. 가설·기각 조건·표본 수를 데이터 수집 전에 커밋했고, 가설이 기각되자 결론을 수정했습니다 (과제 10).
  • 검사를 숫자로 남깁니다. 과제 4·5·6·7·8·13의 자동 검사만 합쳐도 177건(35+10+17+40+43+32)이 모두 통과 상태로 제출되어 있고, 각 과제 상세에 재현 명령을 그대로 남겼습니다.

과제 7 · 플랜두씨 다이어리 2 — 인증과 격리

배포 주소 ↗
2026-09-02 ~ 09-08 · React · Vite · Supabase Auth · PostgreSQL RLS · Vercel

로그아웃한 토큰이 계속 통한다는 JWT의 구조적 약점을 자동 검사로 발견해 DB 정책으로 막았고, 최종 자동 검사 40/40을 통과했습니다. Supabase는 브라우저가 DB REST API를 직접 호출해 공개 키가 번들에 그대로 드러나므로, 계정 간 격리(IDOR)를 화면이 아니라 DB 정책으로 강제했습니다.

문제원인조치검증 결과
로그아웃 후에도 같은 토큰으로 자료 조회JWT는 stateless라 signOut()은 리프레시 토큰만 무효화모든 RLS 정책에 서버 쪽 세션 생존 검사 session_is_active() 추가200 + 내 자료 → 200 + 0건
격리 검사가 스키마 오류(400)를 "거절 성공"으로 오인할 뻔함존재하지 않는 칼럼을 수정 대상으로 지정실제 칼럼으로 교체, 판정 기준을 상태 코드에서 반영 행 수·전후 건수로 강화양방향 0행 반영, 건수 불변
비밀값 탐지 룰 오탐라이브러리 안의 sb_secret_ 접두어 리터럴접두어 + 20자 이상 실제 키 형태만 잡는 정규식으로 정밀화오탐 0건, 탐지 범위 유지
  • 남의 이름으로 저장하는 위조 차단: 요청 본문의 user_id를 무시하고 서버가 auth.uid()로 덮어씁니다.
  • 계정 열거 차단: "계정 없음"과 "비밀번호 틀림" 화면이 파일 해시(MD5)까지 같은 이미지입니다.
  • 검증 중인 항목: 포트폴리오를 정리하며 코드를 다시 읽다가, "내 계정 삭제"가 DELETE 정책이 없는 RLS 테이블에서 오류 없이 0행만 지울 가능성을 발견했습니다. 운영 DB 설정을 아직 확인하지 못해 결함이 아니라 "검증 필요"로 두었습니다.

과제 8 · 내 소개 페이지에 패스키 달기

배포 주소 ↗
2026-09-03 ~ 09-09 · WebAuthn/FIDO2 · SimpleWebAuthn · Vercel Serverless · Neon Postgres

비밀번호 없이 패스키로만 여는 비공개 영역을 만들고, 실사용 중 발견한 삭제 경합과 계정 무한 생성 결함을 재현해 고친 뒤 회귀 검사로 남겼습니다. 최종 자동 검사는 43/43 통과입니다. 패스키가 유일한 자격증명이라 과제 7의 토큰 재사용 문제를 반복하지 않도록 처음부터 JWT 대신 서버 세션 테이블을 택했습니다.

문제원인조치검증 결과
패스키 하나를 지웠는데 계정이 통째로 사라짐삭제 확인 왕복 동안 목록이 살아 있어 삭제 요청 두 개가 나란히 나감삭제 중 목록 전체 잠금, 확인창 개수 변경 시 재확인, 연타 재현 검사 3개 추가계정 소멸 → 하나만 삭제(200 · 1개 유지)
로그아웃 상태에서 계정이 무한 생성됨비로그인이면 무조건 새 계정을 만드는 분기IP당 10분 20회 제한, challenge 발급 단계에서 42925회 연속 호출에서 11번째부터 429 유지
배포 후 공개 주소에서만 검사 실패스키마 변경을 운영 DB에 적용하지 않고 코드만 배포재실행해도 안전한 add column if not exists로 적용41/42 → 42/42
  • 재생·위조·기기 탈취 방어: 사용한 challenge 재전송, 서명 변조, 로그아웃 후 세션 값 재사용을 모두 거절합니다.
  • 파괴적 동작은 세션만으로 허용하지 않음: 패스키 삭제는 5분 이내 재확인을 요구하고, 남의 자료는 404로 존재 여부를 감춥니다.

과제 10 · 논문 — 동기화 패스키의 백업 상태 전이는 서비스에 관측되는가

2026-09-10 · Chrome DevTools Protocol 가상 authenticator · Node.js 측정 스크립트 · 오픈소스 코드 리뷰

패스키 시스템이 "자격증명이 클라우드로 넘어갔다"는 신호(BS 플래그)를 받고도 버리고 있음을 40회 반복 측정으로 입증했고, 신호가 사라지는 지점이 라이브러리가 아니라 그것을 쓰는 응용 쪽임을 소스 조사로 밝혔습니다. 산출물은 논문 1편(표 23개·그림 2개·참고문헌 21건)과 재현 패키지입니다.

  • 가설이 기각되어 결론이 더 날카로워졌습니다. 저장소 소스를 직접 읽자 문제는 라이브러리가 아니라 라이브러리와 응용 사이의 간극이었습니다.
  • 제안은 차단이 아니라 적응형 인증입니다. 막 전이한 자격증명으로 되돌릴 수 없는 동작을 할 때만 추가 인증을 요구합니다.
